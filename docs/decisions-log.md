# Decisions Log

A running record of significant design decisions, why they were made, and when. Newest first once the project is underway — initial decisions are listed together below as the project's starting baseline.

---

## Baseline decisions (project inception)

| Decision | Rationale |
|----------|-----------|
| **Financial year runs September to August** | Matches KHOC's (the first deployment's) financial year convention. Configurable per deployment, but this is the default. |
| **Target reserve uses a three-month rolling average** | Gives a simple, self-adjusting benchmark for a healthy balance without needing a manually maintained target figure. |
| **Signing workflow is toggleable** | Not every use case needs a signed audit trail (e.g. a personal budget tracker). Building it as an optional step keeps the app relevant to multiple use cases without forcing unnecessary steps on users who don't need it. |
| **MFA via authenticator app only — no email-based login** | Authenticator-app TOTP is more secure than email codes (no dependency on email account security or deliverability) and works offline. Keeps the auth surface simple. |
| **Responsive web app only — no native mobile app** | Avoids the cost and complexity of maintaining separate iOS/Android apps. A well-built responsive layout covers the mobile use case (checking the dashboard, uploading a photo of an invoice) without that overhead. |
| **Self-hosted on Proxmox/k3s, cloud-ready when needed** | Keeps hosting costs and data control in the user's hands initially, while the containerised architecture (Docker/docker-compose, k3s-deployable) means a move to a cloud Kubernetes service later is straightforward if needed. |
| **Logo: Option 2 — bar chart with green tick badge** | Chosen over alternative logo concepts as the clearest visual combination of "financial tracking" (bar chart) and "confirmed/accurate" (tick badge), reflecting the app's core value proposition. |
| **Colour scheme inspired by jw.org** | Chosen for its clean, calm, uncluttered aesthetic with generous whitespace — a good fit for a financial tool that should feel trustworthy and easy to read, not busy or overwhelming. |

## 2026-08-04 — Authentication system build

**Decision:** Pending registrations (`POST /auth/register`) get a placeholder role of `standard` at creation, with `approved=false`. The approving Admin confirms or changes the role via `POST /auth/approve-user/{id}`.
**Rationale:** `users.role` is `NOT NULL` in the schema, but a role isn't meaningfully chosen until approval. A placeholder avoids a schema change while keeping "assigns their role" as the Admin's real decision at approval time.

**Decision:** The Superadmin account, bootstrapped from `SUPERADMIN_USERNAME`/`_EMAIL`/`_PASSWORD` env vars at backend startup, is excluded from the "no users exist" check that gates the setup wizard.
**Rationale:** Without this, an env-configured Superadmin would make the users table permanently non-empty, so the first-run setup wizard (which is meant to create the first real Admin) could never run. The Superadmin is a recovery backdoor, not part of normal onboarding, so it's reasonable to treat it as invisible to "has anyone set this up yet."

**Decision:** Added `GET /auth/setup-status` (not in the original endpoint list), an unauthenticated endpoint returning `{ setup_required: bool }`.
**Rationale:** The frontend router needs to decide, before any login attempt, whether to land on SetupPage or LoginPage. There was no other way to answer that question.

**Decision:** `POST /auth/register` now also returns an MFA QR code / secret, shown once on RegisterPage right after submitting (before navigating to PendingApprovalPage).
**Rationale:** Login always requires a TOTP code. Without this, a self-registered user would have no way to ever configure an authenticator app, since only the setup wizard originally showed a QR code — they'd be permanently unable to complete MFA once approved.

**Decision:** `users.mfa_secret` is encrypted at rest (Fernet, key from `MFA_ENCRYPTION_KEY`) and the column was widened from the documented `VARCHAR(64)` to `VARCHAR(255)` (migration `0002`).
**Rationale:** database-schema.md annotates this column "encrypted at rest," but an authenticated ciphertext (nonce + tag + payload) for a TOTP secret doesn't fit in 64 characters. Confirmed with the project owner before deviating from the documented column size — the annotation's intent (real encryption) was judged to matter more than the literal width.

**Decision:** JWT access tokens are split into two scopes: a 5-minute `mfa`-scoped token returned by `/auth/login`, exchanged for an 8-hour `access`-scoped token by `/auth/verify-mfa`.
**Rationale:** Keeps a password-only login from ever being sufficient on its own — the short-lived intermediate token can only be used to complete MFA, nothing else.

**Decision:** Login runs the bcrypt password comparison even when the username doesn't exist (against a fixed dummy hash).
**Rationale:** Otherwise the "no such user" path returns measurably faster than a real password check, letting an attacker enumerate valid usernames by response time.

**Decision:** `.env.example` (root) was updated with the new env vars this feature needs (`SUPERADMIN_*`, `MFA_ENCRYPTION_KEY`, `TOTP_ISSUER`) and `JWT_EXPIRY_MINUTES` was corrected from 60 to 480.
**Rationale:** It's the project's single source of config truth, not documentation — and the security requirements explicitly call for an 8-hour JWT expiry and env-sourced Superadmin credentials.

**Not addressed in this pass:** `main.py`'s CORS middleware uses `allow_origins=["*"]` together with `allow_credentials=True`, a combination browsers reject and that's broader than a deployed instance needs. This predates the auth build; worth tightening to the actual frontend origin(s) when deployment URLs are known.

## 2026-08-04 — Superadmin has no MFA step

**Decision:** `POST /auth/login` skips the MFA step and returns a full access token directly when the authenticating user's stored role is `superadmin`. All other roles (Admin, Standard, Read only) are unaffected and continue through the existing password → `verify-mfa` flow. The response now carries an `mfa_required` flag so the frontend knows which path it's on; `LoginPage` routes straight to the Dashboard when it's `false` instead of to `/mfa`.
**Rationale:** Superadmin is a break-glass emergency recovery account (see [user-roles.md](user-roles.md)) — used when Admin accounts are locked out or forgotten. Requiring TOTP on the one account meant to recover from lockouts risks locking out the recovery path itself (e.g. a lost authenticator device with no other Admin left to help). The branch is decided purely by the `role` column on the row already loaded from the database during password verification — nothing in the request body can reach or influence it, so it cannot be triggered for any other account by client-side manipulation.

## 2026-08-04 — Category management build

**Decision:** The seven default categories are inserted with `op.bulk_insert` inside the Alembic migration (`0003_create_categories_table.py`) that creates the `categories` table, rather than at backend startup like the Superadmin bootstrap.
**Rationale:** Unlike the Superadmin account, the default category list is fixed and not env-driven — there's no configuration to read at runtime. Alembic is the single place where a fresh database's schema and its baseline data are established together, so seeding at migration time keeps "run the migrations" the one step needed to get a fully working install, with no separate seed script to remember.

**Decision:** `DELETE /categories/{id}` deactivates (`active = false`) rather than removing the row, and there is no hard-delete endpoint at all.
**Rationale:** `invoices.category_id` references `categories(id)`; deleting a category a historical invoice points to would either violate that foreign key or silently orphan financial history. Matches the schema doc's own annotation ("Deactivated, not deleted — preserves history") and the feature spec's explicit requirement.

**Decision:** `GET /categories` (active only) is available to any authenticated user, while `GET /categories/all`, create, update, deactivate, and restore are all Admin-only (`require_admin`).
**Rationale:** Every role needs the active category list to classify or filter invoices day-to-day (per [user-roles.md](user-roles.md), all roles can "browse all data"), but only Admin/Superadmin can "manage categories" per that same table — Standard and Read-only cannot add, edit, or deactivate them.

**Decision:** Category names are enforced unique at three layers: a `UNIQUE` DB constraint, an explicit pre-insert/pre-rename check in the router (returning a clear `400` message rather than a raw integrity-error 500), and client-side error display on the Categories page.
**Rationale:** Categories are used consistently for colour-coding across charts and badges — silently allowing duplicate names would make that classification ambiguous. A friendly `400` with a specific message is better than surfacing a database constraint violation to the user.

**Decision:** The Categories page lives at `/settings/categories`, reachable only via a Settings sub-item in the sidebar that's hidden for non-Admins, and the route itself is wrapped in a new `RequireAdmin` guard (`frontend/src/components/RouteGuards.jsx`) — the first role-based (as opposed to purely authenticated) route guard in the app.
**Rationale:** No admin-only route existed yet to model this on; `RequireAdmin` follows the same shape as the existing `RequireAuth`/`RequireGuest` guards but additionally checks `user.role`, so a non-Admin who navigates to the URL directly is redirected to the Dashboard rather than seeing the page flash before data loads.

## 2026-08-04 — Invoice upload and AI extraction build

**Decision:** `invoices.financial_year_id` was created nullable, deviating from database-schema.md's documented `NOT NULL`. A `financial_years` table was added (matching the doc's own schema for that table) purely so the FK target exists, but nothing populates it yet.
**Rationale:** The task brief explicitly asked for `financial_year_id` as "FK, nullable for now" — financial year assignment (opening balance, September–August rollover) isn't built yet, and forcing every invoice to a real financial year row before that exists would mean either a fake placeholder row or blocking the whole invoices feature on unrelated work. Nullable now, tightened to `NOT NULL` once financial year assignment ships.

**Decision:** An `invoices.deleted` boolean (default `false`) was added, even though it isn't in database-schema.md's documented column list.
**Rationale:** The task requires `DELETE /invoices/{id}` to soft-delete, and soft delete needs somewhere to record "deleted" that isn't already spoken for — unlike `categories.active` (which means "still offered for new use," not "deleted"), invoices have no existing flag that fits. Matches the categories precedent of preserving history rather than hard-deleting financial records.

**Decision:** Original PDFs are stored under `{INVOICE_STORAGE_PATH}/original/{year}/{month}/{uuid}_{filename}`, using the already-provisioned `invoice_storage` Docker volume (mounted at `/data/invoices` per `docker-compose.yml` and `.env.example`), rather than the `/app/storage/invoices/original/` path named in the original task brief.
**Rationale:** `docker-compose.yml` already mounts a persistent `invoice_storage` volume at `/data/invoices` — it was provisioned for exactly this purpose ahead of this build. Introducing a second, unmounted `/app/storage` path would either silently not persist across container restarts (defeating the point of a Docker volume) or require a second volume doing the same job as the first. Building on the existing mount keeps one clearly-documented storage location and still satisfies the brief's `{year}/{month}/` + UUID-prefix requirement.

**Decision:** Added `require_standard` to `utils/deps.py` — any authenticated, approved user except Read Only.
**Rationale:** `require_admin` (admin/superadmin only) and `get_current_user` (any authenticated user) didn't cover the "Standard user and Admin only" access level the task specifies for upload, update, and confirm. This is the first "not Read Only" gate in the app; matches the shape of the existing dependencies.

**Decision:** `DELETE /invoices/{id}` allows Standard and Admin to soft-delete an invoice that hasn't been reviewed yet (i.e. discarding a bad upload, as used by the ReviewCard's Discard button), but requires Admin once `reviewed` is `true`.
**Rationale:** The task brief states the endpoint is "Admin only," but the same brief also requires a Discard button on the review card, usable during the review step that Standard users perform themselves per `docs/user-roles.md` ("Standard user: Upload, review, approve, sign, and export invoices"). Read literally, Standard users could review invoices but never discard a bad one without an Admin's help — a Standard-only site would then be unable to use its own required Discard button. Splitting on `reviewed` keeps deleting a *committed, confirmed* financial record as an Admin-only, full-data-control action (matching `docs/user-roles.md`'s "Admin: full access... add/edit/delete data"), while treating discarding a not-yet-reviewed upload as part of the review workflow itself, open to whoever is allowed to review.

**Decision:** AI extraction (`backend/services/ai_service.py`) does not use the Anthropic API's structured-outputs feature (`output_config.format`); instead the prompt asks for a raw JSON object and the response is parsed defensively (strip code fences, `json.loads`, per-field type/range checks), with any failure — API error, unparsable JSON, wrong types — silently degrading to `null`/empty fields rather than raising.
**Rationale:** The configured model (`claude-sonnet-4-6`, per `docs/architecture.md` and `.env.example`'s `ANTHROPIC_MODEL`) isn't on Anthropic's list of models supporting `output_config.format`. Parsing defensively rather than trusting a schema also directly implements the feature spec's own requirement: "If extraction fails or is uncertain, return the fields as empty so the user can fill manually."

**Decision:** `backend/requirements.txt`'s pinned `anthropic==0.34.2` was relaxed to `anthropic>=0.40.0` (resolved to 0.120.2 at build time), breaking from the project's usual exact-pin convention for this one dependency.
**Rationale:** 0.34.2 predates GA support for PDF `document` content blocks (it required an early beta header) and for the JSON/structured-output helpers this feature's extraction prompting relies on. An exact pin would have meant guessing a specific working version number rather than letting pip resolve a current one; the deviation is scoped to this single line, not a project-wide convention change.

**Decision:** Duplicate detection (`check_duplicate` in `ai_service.py`) runs as an ordinary DB query alongside AI extraction, not as a second AI call — same supplier (case-insensitive exact match), invoice date within 7 days, and amount within 2% (or £1, whichever is larger) of an existing non-deleted invoice.
**Rationale:** The feature spec's duplicate criteria ("same supplier, amount, and a close date") are cleanly expressible as a database filter, which is exact, fast, and free — no reason to spend a model call on it or risk the AI inventing a supplier-name match that isn't really the same string.

**Decision:** The frontend adds a plain XHR-based `requestForm` helper in `utils/api.js` alongside the existing `fetch`-based `request`, used only by `invoicesApi.upload`.
**Rationale:** `request()` unconditionally sets `Content-Type: application/json` and `JSON.stringify`s the body, which breaks multipart file uploads; `fetch` also has no upload-progress event, which the task's "upload progress per file" requirement needs. `XMLHttpRequest.upload.onprogress` is the only way to get that in a browser without adding an HTTP client dependency.

**Decision:** PDF preview in the review card is rendered client-side (`pdfjs-dist`, added as the project's first PDF-in-browser dependency) directly from the `File` object still held in memory from the upload `<input>` — not fetched back from the server.
**Rationale:** The backend already has the bytes it needs (PyMuPDF, for text extraction) and doesn't need a "fetch the original PDF" endpoint just to satisfy the review card's preview, since the browser already has the exact same bytes the user just selected. Avoids adding a new authenticated file-serving endpoint for a preview that's only needed in the few seconds between upload and confirm.

**Decision:** No drag-and-drop library was added — `UploadPage.jsx` implements the dropzone with native HTML5 `onDragOver`/`onDrop` events.
**Rationale:** Consistent with the project's minimal-dependency pattern so far (plain `fetch`/`XMLHttpRequest` instead of axios, plain CSS instead of a component library) — native drag-and-drop events are sufficient for a single drop target and don't warrant a dependency.

**Decision:** "AI couldn't determine this field" is inferred on the frontend from sentinel empty values (`supplier === ''`, `amount <= 0`, `category_id === null`) rather than the backend returning an explicit per-field confidence flag.
**Rationale:** `invoices.supplier`, `.amount`, and `.invoice_date` are `NOT NULL` per the documented schema, so the upload endpoint must substitute something when the AI returns nothing — and in real invoice data a supplier can't legitimately be blank or an amount legitimately be zero, so these are safe, unambiguous "needs attention" signals without adding new columns or response fields just to carry a confidence marker.

## 2026-08-04 — PDF signing workflow build

**Decision:** `settings.updated_by` was created nullable, even though the task brief just listed it as "FK users" with no explicit nullability.
**Rationale:** The seeded `signing_enabled=true` default row (migration `0007`) is created by the migration itself, not by any user — a `NOT NULL` FK would have no valid value to put there. Matches the precedent set for `invoices.financial_year_id` (see the invoice upload build above): nullable where a real actor genuinely doesn't exist yet, tightened only if a future requirement needs it.

**Decision:** Signed PDFs are written under `settings.signed_invoice_storage_path` (`/data/invoices/signed/{year}/{month}/{uuid}_{filename}`, on the same `invoice_storage` Docker volume as originals) rather than the `/app/storage/invoices/signed/` path named in the task brief. The `{year}/{month}` used is the **signing date**, not the invoice date.
**Rationale:** `SIGNED_INVOICE_STORAGE_PATH` was already provisioned in `.env.example`, `config.py`, and `main.py`'s startup directory creation ahead of this build, mounted on the same persistent volume as original uploads — an unmounted `/app/storage` path would not survive a container restart. Same reasoning as the original-PDF storage location decision above. Dating the folder by signing date (rather than the invoice's own date, which could be months in the past) keeps the layout meaning "when did this signing event happen," consistent with how `original/{year}/{month}/` is dated by upload time rather than invoice date.

**Decision:** `POST /invoices/{id}/sign` re-checks the `signing_enabled` setting server-side and returns `400` if it's off, rather than trusting the frontend to only call it when enabled.
**Rationale:** The frontend hides the signing panel when the setting is off, but a stale tab or a direct API call could still hit the endpoint after an Admin turns signing off. The backend is the actual source of truth for whether this workflow is currently sanctioned for the organisation.

**Decision:** `sign_invoice_pdf` (`backend/services/signing_service.py`) always opens the *original* PDF and writes a brand-new file under the signed storage path — it never edits the original in place, and the invoice's original `invoice_files.original_path` is left untouched.
**Rationale:** Directly implements the feature spec's "original PDF is always kept — never overwritten" requirement, and matches PyMuPDF's own recommendation not to save a `fitz.Document` back over the file it was opened from.

**Decision:** The signing step is a second, full-width "stage" inside `ReviewCard` (`fields` → `signing`), not a panel shown alongside the editable fields. Clicking through from the fields stage (button reads "Continue to sign" when signing is enabled, or "Confirm" when it's off) saves the edited fields first, then swaps the whole card body for `SigningPanel`. Placing the signature there triggers sign → download → confirm automatically, with no separate manual "Confirm" click in the signing path.
**Rationale:** `docs/features.md` describes the signing step as "Left side: full PDF preview (all pages, scrollable) / Right side: signing controls" — a full layout in its own right, not a sidebar addition to the field-editing view. The task brief's EXPORT section is explicit that download and confirmation happen automatically once signing completes ("Automatically trigger a download... Then proceed to confirm"), so `SigningPanel`'s "Place signature" button is the one action that finishes the whole review.

**Decision:** The draggable/resizable signature box uses a single coordinate model — its position is always stored as `{page, xPct, yPct, wPct, hPct}` (percentages of that page's own width/height) — computed from pointer-drag deltas in absolute pixel space, re-deriving which page the box's centre currently falls into on every move. No drag-and-drop library was added.
**Rationale:** This is what makes cross-page dragging work inside one continuously-scrollable multi-page preview (as opposed to a page-by-page selector), while keeping the `x`/`y`/`width`/`height` values sent to `POST /invoices/{id}/sign` already in the resolution-independent percentage form the endpoint expects. Matches the project's established minimal-dependency convention (plain `fetch`/XHR, no component libraries) — Pointer Events (`onPointerDown`/`onPointerMove`/`onPointerUp`) are sufficient and additionally unify mouse and touch input for both the drag/resize handles and the signature pad itself, satisfying the "must work on both mouse and touch" requirement without separate code paths.

**Decision:** `/settings` and its sidebar entry are gated behind `RequireAdmin` in full (not just the signing toggle control within the page).
**Rationale:** `docs/features.md` describes Settings as "Accessible to Admins (and Superadmin); most settings are Admin-only" — treating the whole page as Admin-only mirrors how `/settings/categories` is already gated, rather than building a partially-visible page for roles that can't act on anything in it.

## 2026-08-04 — Main dashboard build

**Decision:** A `contributions` table was created now (migration `0008`), matching database-schema.md's already-documented shape exactly, even though the task brief's DATABASE section only asked for `planned_projects`. No CRUD endpoints were added for it.
**Rationale:** `/dashboard/summary` is explicitly required to report "total contributions received this financial year (from contributions table — nullable, 0 if none yet)" — that table has to exist for the endpoint to run at all. Building the Contributions feature itself (the `/contributions` page is still a placeholder) is out of scope for this task, so the table exists purely as a read target; it will simply stay empty, and the summary correctly reports £0, until that feature is built.

**Decision:** `planned_projects.expected_month` was built as a `DATE` (first of the month) rather than the `SMALLINT` (1-12, CHECK constrained) documented in database-schema.md, and the table also carries an `active BOOLEAN` column not in that doc.
**Rationale:** Both were explicit, literal requirements of this task's brief ("expected_month (date)", "active (boolean)"), which takes precedence over the older schema doc per the deviation pattern already established in this log (e.g. `invoices.financial_year_id` nullable, `invoices.deleted`). A `DATE` is also strictly more useful here: it disambiguates which calendar year a project's month falls in without leaning on `financial_year_id` (which is nullable), so a project can be forecast into the right month even before it's assigned to a financial year.

**Decision:** The dashboard aggregates invoices and contributions by comparing `invoice_date` (or `contributions.financial_year_id`) against the current financial year's `start_date`/`end_date` range, rather than filtering on `invoices.financial_year_id`.
**Rationale:** `invoices.financial_year_id` is nullable and nothing in the upload/confirm flow has ever populated it (see the 2026-08-04 invoice upload build entry above) — filtering on it would silently show zero invoices for every financial year. Date-range filtering works with the data that actually exists today; `financial_year_id` can be wired up wherever invoice creation is revisited next.

**Decision:** `financial_years` rows are created lazily — `financial_year_service.get_or_create_financial_year()` inserts the row for the current FY (by date-derived label) the first time anything asks for it, rather than requiring a separate financial-year-rollover step to have run first.
**Rationale:** No Settings screen or rollover job creates these rows yet (per `docs/features.md`#8, "Financial year configuration" isn't built). Since the dashboard, and now `planned_projects`/`contributions`, all need a real `financial_years.id` to reference, computing it from `today()` and creating it on first use is what lets the dashboard work from a fresh install with zero manual setup.

**Decision:** `GET /dashboard/notifications` computes its notifications live on every request (balance vs. target, stale unreviewed invoices, unsigned confirmed invoices) rather than reading/writing the `notifications` table documented in database-schema.md. "Dismiss" is frontend-only session state (a dismissed banner reappears on next login if the underlying condition is still true).
**Rationale:** Every notification type in this task's brief is a derived fact about current data ("balance below target," "invoice unreviewed > N days"), not a discrete event a table row would represent well — computing them fresh avoids the row ever going stale or duplicating. The `notifications` table stays available for a future notification type that genuinely is event-shaped (e.g. "duplicate flagged on invoice #123"), which live computation can't express.

**Decision:** The reconciliation-overdue notification is a code comment (in `routers/dashboard.py`), not a notification the endpoint ever emits.
**Rationale:** The task brief itself calls it a "placeholder for reconciliation overdue (reconciliation not built yet)" — the `monthly_reconciliations` table and feature don't exist yet, so there is no data "overdue" could be computed from. Emitting a fake or always-false notification would be worse than leaving a marked TODO for whoever builds reconciliation next.

**Decision:** The "invoices unreviewed for more than N days" notification threshold reuses the existing `UNCONFIRMED_INVOICE_ALERT_DAYS` config value (default 5) instead of a hardcoded 3 days.
**Rationale:** `docs/features.md`#8 already documents this exact threshold as configurable ("Notification thresholds — e.g. how many days an invoice can sit unconfirmed... before it triggers a login notification"), and `config.py` already exposes it. The task brief's "3 days" reads as an illustrative example of that same configurable threshold, not a new, second, hardcoded number — introducing one would leave two competing definitions of the same rule.

**Decision:** `routers/invoices.py`'s private `_signing_enabled()` helper was extracted to `services/settings_service.py` as `is_signing_enabled()`, and `invoices.py` was updated to import it.
**Rationale:** `/dashboard/notifications` needs the same "is signing currently on" check (for the unsigned-invoice notification) that `/invoices/{id}/sign` already had. Duplicating a private, underscore-prefixed helper into a second router would leave two copies of the same rule to keep in sync; moving it to `services/` (where `docs/architecture.md` says business logic belongs) fixes that for both call sites at once.

**Decision:** No charting library was added — the main financial-year chart (`frontend/src/components/FinancialChart.jsx`) is a hand-built inline SVG with a pointer-tracked crosshair/tooltip and legend-button click targets, rather than e.g. Recharts.
**Rationale:** Consistent with this project's established minimal-dependency pattern (plain `fetch`/XHR instead of axios, native drag events instead of a DnD library, Pointer Events for the signing canvas). A 12-point line/area chart is well within what plain SVG + React state can do cleanly, and it keeps the three click-through targets (income/spend/forecast) fully under the app's own control rather than fighting a library's event model.

**Decision:** Series colours are blue `#2D6B9F` (income), green `#1D9E75` (actual spend), amber `#C97A0C` (forecast), purple `#7C5CBF` (planned-project markers) — the first two are the existing brand primary/accent; amber and purple are new. All four were run through a categorical-palette colourblind/contrast validator before use.
**Rationale:** The task brief specified blue/green/amber/distinct-colour by role; amber `#C97A0C` and purple `#7C5CBF` were chosen to pass CVD-safe separation (protan/tritan ΔE ≥ 8, normal-vision floor ≥ 15) against the other three and against the app's off-white surface, rather than picking visually-plausible hex values by eye.

**Decision:** A new `/forecast` route (`ForecastBreakdownPage.jsx`) was added, reachable only by clicking the forecast series on the dashboard chart — it is not in the sidebar.
**Rationale:** `docs/features.md` requires "Click the forecast line to see a breakdown by category," and no such view existed. Not adding it to the sidebar matches how `InvoiceDetailPage` (reached only via the Invoices table) already works — a drill-down view, not a top-level destination.

**Decision:** `InvoicesPage.jsx` now reads its initial `categoryId`/`dateFrom`/`dateTo`/`reviewed` filter state from the URL's query string (`useSearchParams`, read once on mount) instead of always starting blank.
**Rationale:** The dashboard's "click actual spend → Invoices filtered to this financial year" and the unreviewed-invoices notification link both need to land on Invoices pre-filtered. Without this, every drill-down link into Invoices would silently drop its filter the moment the page loaded.

## 2026-08-04 — Contributions recording and monthly reconciliation build

**Decision:** `contributions.deleted` (boolean, default `false`) was added via migration `0010`, even though it isn't in database-schema.md's documented column list.
**Rationale:** The task requires `DELETE /contributions/{id}` to soft-delete, and — exactly as with `invoices.deleted` — there was no existing column that meant "deleted" rather than something else. Matches the precedent set for invoices: preserve financial history rather than hard-delete it.

**Decision:** `financial_years.opening_balance` (`NUMERIC(12,2)`, nullable) was added via migration `0011`, not documented in database-schema.md.
**Rationale:** The task's OPENING BALANCE section requires `PUT /financial-years/{id}/opening-balance`, but the existing `financial_years` table (built for the dashboard) had nowhere to store it. Nullable because a financial year starts with no opening balance set — the dashboard and Contributions page prompt for it until an Admin sets one.

**Decision:** `monthly_reconciliations.month` is stored as a `DATE` (first of the month), and `notes` is split into two columns, `discrepancy_notes` (user-entered) and `suggested_reason` (system-generated) — both deviating from database-schema.md's `month SMALLINT` and single `notes TEXT`.
**Rationale:** These were explicit, literal requirements of this task's brief, which takes precedence per the deviation pattern already established in this log (e.g. `planned_projects.expected_month`). Storing the two reasons separately also lets the suggested reason stay intact and re-derivable even after a user edits their own notes.

**Decision:** `calculated_balance` for a given month is computed live (not read from a stored running total) as `opening_balance + contributions recorded in months up to and including this one − confirmed invoices dated on or before the end of this month`, all scoped to one financial year. The same function (`services/reconciliation_service.calculated_balance_for_month`) backs both the Reconciliation page's per-month figure and the Contributions page's "running balance" column.
**Rationale:** Directly implements docs/features.md#4's formula ("money on hand = opening balance + contributions to date − invoices to date"), evaluated as of a specific past month rather than always "today" — a reconciliation for October needs October's balance, not the current one. Sharing one function between both pages means they can never silently disagree with each other about what "balance so far" means.

**Decision:** `POST /reconciliation` rejects a second submission for a month that's already been reconciled (`400`), rather than overwriting it. `PUT /reconciliation/{id}` only ever updates `discrepancy_notes` — the actual balance, calculated balance, and discrepancy are fixed at submission time.
**Rationale:** The task brief lists PUT's scope as "update discrepancy notes" only, with no endpoint for correcting a submitted actual balance. Treating a reconciled month as locked (bar its notes) keeps the reconciliation history an honest audit trail of what was actually checked against the bank each month, rather than a value that can quietly drift after the fact. A wrong entry needs an Admin to intervene directly rather than being silently overwritten via the API.

**Decision:** The "small vs. large" discrepancy threshold (`SMALL_DISCREPANCY_THRESHOLD` in `services/reconciliation_service.py`) is a fixed `£20`, not user-configurable.
**Rationale:** The task brief specifies the suggested-reason categories ("small positive," "large," etc.) without giving a threshold figure. £20 is a reasonable, round default for the scale of a small charity's bank interest/charges; making it a Setting is future work once the terminology/settings system referenced in the task brief exists.

**Decision:** `Contribution.recorded_by` and `MonthlyReconciliation.reconciled_by` are always set from the authenticated user (`Depends(require_standard)`), never from the request body, even though the task brief lists `recorded_by` among `POST /contributions`'s payload fields.
**Rationale:** Matches the existing `invoices.created_by` precedent — trusting a client-supplied "who did this" field would let one user record a contribution or reconciliation under another user's name. The brief's field list reads as documenting the column being populated, not as a literal request-body requirement.

**Decision:** Added `GET /financial-years/current` (not in the original endpoint list), any authenticated user, returning the current financial year including its opening balance (creating the row lazily if needed, same as the dashboard's existing behaviour).
**Rationale:** The Contributions and Reconciliation pages both need to know the current financial year's id and opening-balance status without pulling in the whole `/dashboard/summary` payload. Mirrors the precedent set by `/auth/setup-status` — a small lookup endpoint added because the frontend had no other way to answer a question it needed answered before rendering.

**Decision:** `DashboardFinancialYear` (and `/dashboard/summary`'s response) now also carries `opening_balance`, and the Dashboard shows its own "no opening balance set" amber prompt banner.
**Rationale:** The task brief explicitly asks for the prompt to appear "on the dashboard and contributions page." Reusing the field already being returned for the financial year avoids a second round-trip from the Dashboard just to check one value.

**Decision:** `ReconciliationPage.jsx` loads all 12 months of the financial year up front via 12 parallel calls to `GET /reconciliation/{year}/{month}`, rather than adding a bulk "all months" endpoint.
**Rationale:** No bulk endpoint was in the task's endpoint list, and each month's tile (reconciled/overdue/discrepancy colour) needs the same per-month shape `GET /reconciliation/{year}/{month}` already returns — including a live `calculated_balance` for months that haven't been reconciled yet, which the "list reconciliations" endpoint alone can't provide since it only has rows for months already reconciled.

**Rationale:** Matches the project's "fully manageable within the app" philosophy (`docs/project-overview.md`) better than a container-restart-requiring env var, and reuses infrastructure the settings page already exposes rather than adding a report-specific site-name field.

**Rationale:** `categories_included` is genuinely "a list of category ids, empty means all," per the task brief's own column description, and `parameters` needs to capture an arbitrary, growing set of generation options verbatim for later reference — normalising either into extra tables would add real complexity for a value that's never queried by field, only ever read back whole as part of one report's own metadata. The engine is Postgres-only (`docs/architecture.md`), so `JSONB` costs nothing in portability.

**Rationale:** Same precedent as `invoices.deleted` / `contributions.deleted` — the task brief specifies delete as "soft delete," and there was no existing column that already meant "deleted."

**Decision:** `POST /reports/generate` (and `GET`/download) requires only `get_current_user` — no `require_standard` gate — making it the only generation/write-shaped endpoint in the app open to Read Only accounts.
**Rationale:** `docs/features.md`#6 and #7 are explicit and repeated: "Access: any user role, including Read Only, can run and export a report" / "All roles can run and export reports." A report is read-only output over existing data (nothing it does is persisted as financial history the way an invoice or contribution is), so this doesn't conflict with Read Only's "cannot add or change anything" restriction elsewhere.

**Decision:** `report_service.py` treats the request's `date_from`/`date_to` as the scope for the report's own totals, monthly chart, category breakdown, and funding position, but `years_included` independently controls a *separate* lookback window (the last N financial years counting back from the FY containing `date_to`) used only for the "annual totals by category" chart and year-on-year comparison.
**Rationale:** The task brief lists both `date_from`/`date_to` and `years_included` as independent parameters ("years_included (integer, how many financial years to show, default 3)") — collapsing them into one range would make a short date range (e.g. "last quarter") unable to also show a multi-year annual comparison, which is exactly the kind of report a trustee is likely to want.

**Decision:** Contributions are dated for a report by resolving each row's `financial_year_id` + 1–12 `month` number against that financial year's own month sequence (`financial_year_service.month_sequence`), the same mapping already used by the dashboard and reconciliation.
**Rationale:** `contributions` has no date column of its own (see `database-schema.md`) — this was the only existing, already-trusted way to turn a contribution into a real calendar date for range filtering, and reusing it means a report's contribution figures can't quietly disagree with the Contributions page's own monthly summary about which month a contribution falls in.

**Decision:** The forecast's per-category breakdown table lists a category's monthly average and forecast total, but planned project costs — which aren't tied to any one category — are shown as a separate "Planned projects (all categories)" row appended to the same table, rather than folded into any category's figure or omitted.
**Rationale:** Caught during visual review of a generated PDF: the "Actual vs. forecast" chart's forecast bar included planned project cost (per `financial_year_service`-style forecasting), but the by-category table below it summed to a smaller figure with no visible reconciliation, which would read as a data error to anyone checking the numbers against each other. **Decision:** The AI report-summary prompt (`services/ai_service.py::generate_report_summary`) is given a hand-formatted plain-text digest of the already-calculated figures (`_build_report_context`), not a raw JSON dump of the report data structure, and is explicitly instructed not to invent numbers or restate every figure verbatim (the PDF already shows them in tables/charts alongside the AI text).
**Rationale:** The task brief requires the prompt to include financial year dates, category names, site name, and "clear instructions to write for a non-technical audience" — a formatted digest is both easier for the model to read correctly and answers docs/features.md#6's "written narrative summary suitable for a general audience" requirement directly, whereas a raw data dump risks the AI re-deriving or misreading numbers report_service.py already computed correctly.

**Decision:** `generate_report_summary` follows the exact same graceful-degradation contract as invoice extraction (`ai_service.EMPTY_EXTRACTION` / now `EMPTY_REPORT_SUMMARY`): any failure (no API key, API error, unparsable JSON response) returns all-empty fields rather than raising, and `POST /reports/generate` still completes and returns `201` with figures, tables, and charts intact — only the AI narrative sections are left blank in the PDF ("An AI-written summary was not included with this report."). Verified directly: this repo's `.env` has a placeholder `ANTHROPIC_API_KEY`, so every report generated during this build's testing exercised this exact path.
**Rationale:** Matches the existing project-wide rule (`docs/decisions-log.md`, invoice upload build) that AI failures degrade gracefully rather than blocking the feature — a report is still useful as a figures-and-charts document even without the written summary, so a transient AI/API failure shouldn't prevent generating one.

**Decision:** The ReviewCard's fields-stage thumbnail is now rendered server-side (`GET /invoices/{invoice_id}/preview`, `backend/services/preview_service.py`, PyMuPDF) instead of client-side with pdf.js (`renderPdfFirstPage` in `frontend/src/utils/pdf.js`, no longer used there). The signing stage keeps using the existing full pdf.js renderer (`SigningPanel`, via `loadPdfDocument`/`renderPdfPage`) unchanged.
**Rationale:** The client-side thumbnail was not applying a PDF's `/Rotate` page metadata, so invoices scanned or exported in a rotated orientation previewed upside down and cropped. PyMuPDF's `page.get_pixmap()` bakes a page's own rotation into its default rendering matrix — confirmed directly by rendering a `/Rotate 90` test PDF and inspecting the output — so no manual rotation math is needed or correct to add on top of it. The signing panel was left alone because it isn't the reported bug: it already renders every page correctly (pdf.js's `getViewport()` also defaults to the page's own rotation), and this task's brief explicitly asked for it to be unaffected.

**Rationale:** Stored PDFs live at `INVOICE_STORAGE_PATH/original/{year}/{month}/{uuid}_{filename}` (see the invoice upload build entry above), not as a flat `{filename}`, so a bare filename parameter can't address a file without either reconstructing that path from an untrusted client-supplied string (a path-traversal risk) or a second filename→path lookup table that doesn't otherwise exist. `invoice_id` is already the trusted identifier the frontend has at this point (the review stage's invoices are already created server-side by `/invoices/upload` before ReviewCard renders), and reusing it keeps this endpoint's access control and file-resolution logic identical to the two sibling endpoints instead of inventing a second scheme.

This is the same constraint that already led to `requestBlob`-based downloads for the signed and original PDFs; the preview follows the same pattern rather than being a real exception to "img tag pointing to the endpoint."

**Tested:** Verified against the running dev containers — uploaded a PDF with `/Rotate 90` set (previously reproducing the upside-down/cropped bug on this code) via a Playwright-driven browser session logged in as Superadmin. No console errors were observed. Test invoices created during verification were deleted afterwards.

## 2026-08-05 — App start date setting (hide phantom empty months)

**Decision:** `settings.value` (`backend/models/setting.py`) was widened from `NOT NULL` to nullable (migration `0015`), rather than representing "not set" with a sentinel string. `app_start_date` is seeded as a `NULL` row by the same migration.
**Rationale:** The task brief is explicit that "not set" is a real state (`value=null`), not a special string a caller would have to know to check for. Every other seeded setting (`signing_enabled`, `site_name`) still gets a real value at insert time, so this only changes what's *possible*, not what's *seeded*, for existing settings.

**Decision:** `PUT /settings/{key}` keeps requiring a non-empty `value` (`SettingUpdate.value: str`, unchanged); a new `DELETE /settings/{key}` was added instead, which sets `value` to `NULL` rather than removing the row.
**Rationale:** A generic nullable `PUT` body would let an Admin accidentally blank out `signing_enabled` or `site_name` through the same endpoint that manages `app_start_date`. Splitting "set a value" (`PUT`) from "clear back to not-set" (`DELETE`) keeps the existing settings' validation exactly as strict as before, while giving `app_start_date`'s "Clear" button (and any future nullable setting) a properly-scoped, REST-shaped way to do it — matching the project's existing soft-delete convention (`DELETE` meaning "reset/deactivate," not "remove the row").

**Decision:** `services/date_service.py` (`get_effective_start_date`) does not import `services/financial_year_service.py` for its "start of the current financial year" fallback — it recomputes that one calculation (a few lines, from `config.default_financial_year_start_month`) locally instead.
**Rationale:** `financial_year_service.build_summary` needs `get_effective_start_date` to filter its own monthly breakdown, so importing in the other direction (`date_service` → `financial_year_service`) would create a circular import. The duplicated logic is small and self-contained enough that this was judged better than restructuring either module.

**Decision:** `GET /dashboard/summary`'s `monthly_breakdown` is filtered to months from `app_start_date` onwards, and `monthly_average_cost` is recalculated from only that visible, elapsed portion (visible elapsed spend ÷ visible elapsed months) — but `total_spent`, `total_contributions`, `current_balance`, and `target_reserve` are left as whole-financial-year figures, unfiltered by `app_start_date`.
**Rationale:** `app_start_date` is a display setting ("months before this date are hidden"), not a data-scoping one — the actual money on hand doesn't change because a UI preference hides some rows, and recomputing the real balance off a display cutoff risked making it *wrong* rather than just less cluttered. `monthly_average_cost` is the one figure that's derived from the breakdown loop itself, so recalculating it from only the visible months is what makes it read as "average since you started tracking" instead of being silently diluted by hidden months with no invoices — this also fixes a real (if minor) accuracy issue for anyone starting Keep Track partway through a financial year, independent of the phantom-rows complaint that prompted this task.

**Decision:** `GET /dashboard/notifications` was not changed. The task's "do not flag reconciliation overdue for months before app_start_date" requirement has no code to change against — the reconciliation-overdue notification was never built (see the main dashboard build entry above: "intentionally not generated yet... This is the placeholder for it"). A one-line comment was added next to that existing placeholder pointing whoever builds it at `date_service.get_effective_start_date`.
**Rationale:** Matches this log's own established practice of noting "not addressed" rather than writing dead logic against a feature that doesn't exist yet (see the auth build entry's CORS note, and the main dashboard build's identical placeholder-comment approach for this same notification).

**Decision:** The setup wizard's new "When did you start using Keep Track?" step (`SetupPage.jsx`, after the QR-confirm step) saves via a new, dedicated, unauthenticated endpoint — `PUT /auth/setup/app-start-date` — rather than the standard Admin-only `PUT /settings/{key}`. **Rationale:** `POST /auth/setup` never logs the new Admin in — by design, per the earlier auth build entry, Admin accounts always need a verified TOTP code, which the wizard's QR-confirm step ("I've scanned it") never actually collects. So there is no access token available at the point this step runs, and the standard settings endpoint (`require_admin`) can't be used. `sole_setup_admin` is deliberately the same shape and risk level as `no_setup_users_exist` (the gate already protecting `POST /auth/setup` itself, equally unauthenticated) rather than a new security model: both close permanently and automatically the moment real multi-user activity starts, and `app_start_date` is a low-stakes display preference, not sensitive data, so this narrow reuse of the existing "still mid first-run-setup" trust window was judged proportionate rather than needing a full login flow bolted onto the wizard.

**Decision:** `ContributionsPage.jsx`'s "All entries" list and `ReconciliationPage.jsx`'s month tiles filter out months before `app_start_date` client-side (via a shared `useAppStartDate` hook and `isMonthVisible` helper), even though the backend only filters `GET /contributions/monthly-summary` and `GET /reconciliation` (bulk list) per the task brief. `GET /contributions` (plain list) and `GET /reconciliation/{year}/{month}` (per-month) were left unfiltered.
**Rationale:** The task brief's "hidden across the entire app" scope is broader than the two specific endpoints it names, and both pages have their own additional month-shaped views (the raw entries list; the 12 fetched-but-not-yet-reconciled month tiles) that the two named endpoints don't cover on their own. Filtering the *endpoints* that back the all-months list/bulk views was judged the right backend-side change (per the brief); filtering client-side for the other two, already-role-open, already-authenticated views reaches the same "hidden across the app" outcome without adding new backend endpoints or query parameters the brief didn't ask for.

## 2026-08-05 — Admin unlock for reconciled months and completed projects

**Decision:** `PUT /reconciliation/{id}` now accepts optional `actual_balance` and `edit_reason` alongside the existing `discrepancy_notes`, all three now optional on `ReconciliationUpdate` (previously `discrepancy_notes` alone, required). Supplying `actual_balance` requires the caller to be Admin/Superadmin (else `403`) and requires a non-empty `edit_reason` (else `400`); the endpoint then recalculates `calculated_balance`/`discrepancy`/`suggested_reason` from scratch (via the existing `calculated_balance_for_month`/`suggest_reason`) and stamps new `edited_by`/`edited_at`/`edit_reason` columns (migration `0016`). A plain `discrepancy_notes`-only call (any Standard/Admin, no reason) still works exactly as before.
**Rationale:** The previous build's own decision log entry (2026-08-04, contributions/reconciliation build) deliberately locked a submitted reconciliation's actual balance "bar its notes" specifically because no Admin-override endpoint existed yet — this task is that override. Recalculating from the same helper functions the original `POST` uses (rather than letting the caller submit a discrepancy directly) keeps the two code paths unable to disagree about what a given actual balance implies.

**Decision:** `PUT /projects/{id}` now checks `project.completed` before applying any change. If completed, the request is rejected (`403`) unless the caller is Admin/Superadmin **and** sent `admin_override: true`, and a non-empty `edit_reason` (`400` otherwise). In that path only `name`, `description`, and `estimated_cost` are ever written — `expected_month` and `financial_year_id` are silently ignored even if present in the payload — and `edited_by`/`edited_at`/`edit_reason` (migration `0017`) are stamped. A changed `estimated_cost` also writes a human-readable `admin_edit_notes` column recording the previous figure (e.g. "Previous estimated cost: £1750.50").
**Rationale:** Investigating this task's premise ("completed projects are fully locked") found the router actually had no completed-project check at all — any Standard user could already edit a completed project's every field via the plain `PUT`, contradicting `docs/features.md`#5's "marked complete... removes it from the active list" framing. This task both adds the requested Admin override and fixes that pre-existing gap in the same change, rather than bolting the override onto a lock that didn't really exist. `admin_edit_notes` is a dedicated column (not reusing `description`) so the audit trail survives even if an Admin also edits the description in the same request.

**Decision:** `edited_by`/`edited_at`/`edit_reason` were added to both tables as genuinely nullable columns (no server default), left `NULL` for every row that has never been admin-corrected, rather than e.g. defaulting `edited_at` to the row's creation time.
**Rationale:** Matches the project's existing "nullable where a real actor genuinely doesn't exist yet" precedent (`settings.updated_by`, `invoices.financial_year_id`) — most reconciliations and completed projects will never be corrected, and a populated-by-default column would make "has this been edited?" indistinguishable from "was this just created."

**Decision:** The frontend's `reconciliationApi.update(id, payload, token)` now takes a full payload object instead of a bare `discrepancyNotes` string, matching `projectsApi.update`'s existing shape. `ReconciliationPage.jsx`'s existing "Save notes" call site was updated to `{ discrepancy_notes: notesInput }` — the only caller affected.
**Rationale:** The Admin correction form needs to send `actual_balance`/`edit_reason` alongside notes on the same endpoint; a helper hard-coded to one field can't express that, and a second bespoke helper for the same endpoint would be worse than making the existing one generic.

**Decision:** Both new admin-edit forms (`ReconciliationPage.jsx`, `ProjectsPage.jsx`) use a local two-stage `step: 'form' | 'confirm'` on submit — the first submit swaps the button row for an inline "Are you sure...? This action will be logged." confirmation, the second actually calls the API — rather than a browser `window.confirm()`.
**Rationale:** No `window.confirm()` call exists anywhere else in the codebase; every other destructive/consequential action already in the app (`ProjectCard`'s "Mark complete?"/"Deactivate?") uses this same inline two-click pattern via a `confirmAction` piece of state. Matching it keeps the new confirmation step visually and behaviourally consistent with the ones already shipped.

**Decision:** The completed-project Edit button/form was added to `ProjectCard` behind a new `onAdminEdit` prop, rendered only when `readOnly && isAdmin && onAdminEdit` — the existing `!readOnly && canManage` action block (Edit/Mark complete/Deactivate for active projects) was left untouched.
**Rationale:** `ProjectCard` already renders completed projects with `readOnly` (no actions at all) — adding a second, narrower action block conditioned on admin-ness was simpler and lower-risk than threading a "is this the completed list" flag through the existing action block's logic.

## 2026-08-05 — Configurable financial year start month

**Decision:** The financial year start month moved from `config.py`'s `default_financial_year_start_month` (an env-only, restart-required constant) to a `financial_year_start_month` row in the existing `settings` table (migration `0018`, seeded `"9"`), read via a new `services/settings_service.get_financial_year_start_month()` helper — the same fallback-to-env-default pattern already used by `is_signing_enabled`. `config.default_financial_year_start_month` is kept only as that helper's fallback if the settings row is ever missing/unset, and `default_financial_year_end_month` was removed from `config.py`/`.env.example` entirely (see next decision).
**Rationale:** `docs/features.md`#8 already documented "Financial year configuration" as a Settings-page feature, but the value had only ever been a startup-time env var — an Admin couldn't change it without editing `.env` and restarting containers. Moving it into `settings` (already the pattern for `signing_enabled`, `site_name`, `app_start_date`) makes it a genuine runtime setting reachable from the Settings page and the setup wizard, per this task's brief.

**Decision:** `financial_year_service.fy_bounds_for()` no longer takes a separate end-month config value — the FY end month is always derived as the month immediately before the start month (wrapping December → January), since a financial year is always exactly 12 months. This surfaced a latent bug while testing a January start month: with the old "always add 1 to end_year" logic (correct only when the FY crosses a calendar-year boundary, e.g. Sep 2025 → Aug 2026), a January-start FY was computed as Jan 2026 → Dec **2027** instead of Jan–Dec 2026. Fixed by only advancing `end_year` when the start month isn't January (the one case where the FY doesn't cross into a second calendar year).
**Rationale:** A single source of truth for the end month (derived, not independently configured) removes a class of bug where the two values could disagree; the January-start case is exactly the kind of edge case that configurable start months need to handle correctly, not just the Sep-Aug default KHOC already uses.

**Decision:** The financial year label changed shape from a bare `"2025/26"` to `"FY2025/26 (Apr–Mar)"` (or, for a January start month specifically, `"FY2026 (Jan–Dec)"` — no slash, since that FY doesn't span two calendar years), per this task's explicit example format. `FinancialYear.label` stays `VARCHAR(20)` (migration `0004`, unchanged) — confirmed the longest possible value (`"FY2025/26 (Sep–Aug)"`, 19 characters) still fits.
**Rationale:** The old bare-year label gave no indication of which months a financial year actually covered once the start month became configurable — "2025/26" is ambiguous between a Sep-start and, say, a Nov-start FY. Every UI surface already interpolates `fy.label`/`financial_year.label` as opaque text (`frontend/src/pages/*.jsx`, the reports PDF), so the richer label needed no separate frontend changes to show up everywhere at once.

**Decision:** Because `get_or_create_financial_year()` looks up an existing `financial_years` row by `label`, and the label now encodes the start month, changing the setting doesn't rewrite any existing `financial_years` row — the very next lookup (with different bounds) simply fails to match any existing label and lazily creates a new row alongside the old one, exactly like the dashboard already did for a brand-new FY. Switching back to the original start month re-matches the original label and reuses the original row untouched.
**Rationale:** This is what the Settings page's own required warning ("Existing financial year records will not be changed automatically") describes, and it falls out of the existing lazy-creation design (see the 2026-08-04 main dashboard build entry) for free — no explicit "don't touch old rows" logic had to be written. Verified directly: setting the start month to January created a new FY row and left the original Sep-Aug row's reconciliation history (`financial_year_id=1` rows) exactly as it was; reverting to September re-selected the original row rather than creating a third one.

**Decision:** The setup wizard's existing unauthenticated `PUT /auth/setup/app-start-date` step (see the 2026-08-05 app start date entry) gained an optional `financial_year_start_month` field on the same request/response, rather than adding a second unauthenticated endpoint for the new dropdown this task adds to that same step.
**Rationale:** The task brief places the financial year start month "as part of Step 3 alongside the app start date" — one wizard step, one form. The endpoint's `sole_setup_admin` gate (only usable while the just-created Admin is still the only non-Superadmin user) is identical for both fields, so a second endpoint would duplicate that gate for no benefit; a single call setting both settings keeps the step's "Confirm" button doing one thing.

**Decision:** `PUT /settings/financial_year_start_month` gained a special-cased server-side check (in `routers/settings.py`, alongside the otherwise fully generic `PUT /settings/{key}`) rejecting any value outside `"1"`-`"12"` with `400`, mirroring the `ge=1, le=12` validation already added to the setup wizard's Pydantic field for the same setting.
**Rationale:** Every other setting's value is either free text (`site_name`) or a `"true"`/`"false"` string nothing else depends on; `financial_year_start_month` drives real date arithmetic (`monthrange`, year rollovers) throughout `financial_year_service.py`, so an out-of-range or non-numeric value would raise deep inside that logic rather than failing cleanly at the point of entry.

**Decision:** `ContributionsPage.jsx`, `ReconciliationPage.jsx`, `FinancialChart.jsx`, and every other frontend surface that reads `fy.start_date`/`fy.label`/`month_label` needed **no code changes** for this task — `monthsInFinancialYear()` (`frontend/src/utils/format.js`) already walks 12 months forward from `fy.start_date`, and the dashboard chart's x-axis already renders whatever `month_label` strings `GET /dashboard/summary` returns, so both were already start-month-agnostic once the backend computed the right `FinancialYear` row.
**Rationale:** This was verified, not assumed — confirmed by reading `monthsInFinancialYear`'s implementation and by end-to-end testing (Playwright session against the running dev containers): switching the setting to January immediately reorganised the Dashboard, Contributions, and Reconciliation pages around Jan–Dec with zero frontend edits, which is what "any financial year label shown in the UI should use the dynamic label" and "chart X axis shows the correct 12 months" turned out to already mean in practice, once the one shared backend service was fixed.

**Tested:** Verified against the running dev containers via a Playwright-driven browser session logged in as Superadmin. On the Settings page, changed "Financial year start month" from September to January — the amber warning ("Changing the financial year start month will affect how all historical data is grouped and displayed...") appeared before the two-step "Confirm change"/"Cancel" buttons, matching the same confirm pattern used elsewhere in Settings. ## 2026-08-05 — Full terminology system and configurable target reserve

**Decision:** Six settings rows — `term_expenses`, `term_income`, `term_projects`, `term_reconciliation`, `term_reserve` (migration 0019) and `site_name` (already seeded by migration 0014, left untouched) — are read together by a new `services/settings_service.get_terminology(db)` helper and exposed as a single object via `GET`/`PUT /settings/terminology`, rather than requiring the frontend to assemble them from the generic `GET /settings` list.
**Rationale:** The frontend needs all six as one atomic object on every app load (to render the Sidebar, Header, and page titles before anything else renders), and the task brief's "update one or more terminology settings at once" requirement doesn't fit the existing generic `PUT /settings/{key}` (one key per call). `GET /settings/terminology` is open to any authenticated user (not Admin-only) — matching the brief's explicit reasoning: every role needs these labels to render navigation, not just Admins who can change them.

**Decision:** `term_reserve` was added as a sixth editable field in the Settings page's Terminology section, even though Part 1's "Fields for each configurable term" bullet list named only five (Expenses, Income, Projects, Reconciliation, Site/instance name).
**Rationale:** `term_reserve` is explicitly one of the six settings the DATABASE section asks for, and Part 2's Target Reserve section says its "Label field... uses term_reserve from terminology (so it updates automatically when terminology is changed)" — implying the field is edited elsewhere and merely *displayed* there. Treating the five-item bullet list as incomplete (rather than deliberately excluding reserve-label editing from the app entirely) was judged the more coherent reading, and it's what makes all six seeded settings actually reachable from the UI.

**Decision:** The target reserve's "automatic" calculation keeps a fixed, non-configurable 3-month rolling-average window for "average monthly spend" (a new `financial_year_service.average_monthly_spend()`, factored out of the old `target_reserve()`), and only the **multiplier** (`reserve_months`, 1–12, default 3) is configurable — rather than making the averaging window itself the configurable "months" value.
**Rationale:** The original hardcoded behaviour was a 3-month average multiplied by... itself (used as both the window and the implicit "target = 3 months of spend"). The task brief's Part 2 wording — "target = rolling average monthly spend × reserve_months" and a Settings UI control explicitly labelled "months multiplier" — describes two distinct numbers, not one. Decoupling them means changing the multiplier to 6 targets six months of reserve without changing what "average monthly spend" means, and reproduces the exact original behaviour when left at its default (3-month window × 3 months multiplier = the old formula, unchanged for anyone who doesn't touch the new setting).

**Decision:** `target_reserve(db, today)` now returns a `(Decimal, dict)` tuple — the amount plus the resolved `{calculation, months, manual_amount}` settings — instead of a bare `Decimal`, so `financial_year_service.build_summary()` (its only caller) can report `reserve_calculation`/`reserve_months` in `/dashboard/summary` without a second settings read.
**Rationale:** The task brief requires the summary response to include the calculation method and months multiplier alongside the amount. Reading the settings twice (once inside `target_reserve`, once again in `build_summary`) risked the two reads disagreeing if a value changed between them; returning the resolved settings from the one read avoids that.

**Decision:** `GET /dashboard/notifications`'s balance-warning messages and unreviewed/unsigned-invoice messages now interpolate the live `term_reserve`/`term_expenses` settings (lower-cased, with a small `_singularize()` helper for count-based phrasing) instead of the hardcoded words "target reserve" and "invoice(s)".
**Rationale:** These notification banners are backend-generated strings, not frontend components — the frontend can't retroactively rename a word baked into a string it just renders verbatim. Since the backend already has DB access via `settings_service`, having it speak the organisation's configured vocabulary was the only way to satisfy the task's "notification banners must use the hook instead of a hardcoded label" requirement for banners whose text originates server-side.

**Decision:** The frontend's `TerminologyContext` (`frontend/src/context/TerminologyContext.jsx`) only fetches `GET /settings/terminology` when a user is logged in (`user?.token` present); pre-login routes (Login, Setup, Register) see the hardcoded `TERMINOLOGY_DEFAULTS` instead of a fetch attempt.
**Rationale:** The endpoint requires authentication (any logged-in user, not anonymous), and none of the pre-login pages render the Sidebar/Header/Layout that actually display these labels — there's nothing for a pre-login fetch to accomplish, and attempting one would just log a spurious 401 on every login/setup page load.

**Decision:** `TerminologyContext` exposes a `loading` flag distinct from its `term_*` values (which are always populated, defaulting to `TERMINOLOGY_DEFAULTS` before the fetch resolves), and the Settings page's Terminology form only seeds its editable inputs from context once `loading` is `false`.
**Rationale:** Without this, the Terminology form would briefly seed itself from the placeholder defaults (identical in shape to real data, so nothing would visibly fail) and then never re-sync once the real fetch landed a moment later — an Admin editing quickly after page load could unknowingly overwrite a genuinely-customised label back to its default on save.

**Decision:** Best-effort singular helpers (`frontend/src/utils/format.js`'s `singularize()`, and a near-identical private `_singularize()` in `backend/routers/dashboard.py`) strip a trailing `-ies`/`-s` to turn a configured plural label into a singular one for phrases like "Upload invoice" / "1 invoice still waiting" — duplicated rather than shared across the frontend/backend language boundary.
**Rationale:** Every configured term ships as a plural noun ("Invoices," "Contributions"), but several UI strings need the singular ("+ Upload invoice," "Untitled invoice," a count of exactly 1). A plain suffix-stripping heuristic isn't linguistically perfect for every conceivable custom term an Admin might type, but it correctly handles the shipped defaults and any ordinary plural rename, which was judged sufficient without adding a pluralisation library for either language.

**Decision:** Not every occurrence of the words "invoice"/"contribution"/"project"/"reconciliation" in the frontend was converted to use the terminology hook — only the categories the task brief explicitly listed (sidebar links, page titles/headings, notification banners, dashboard panel headings, empty states, breadcrumbs/back links) plus the small set of quick-action buttons and loading states needed for those pages to read consistently. Inline form field labels (e.g. "Invoice date," "Discrepancy notes"), generic error-fallback strings (e.g. `catch` block messages), and descriptive body copy (e.g. Projects page's "a project, a purchase, a repair") were left as-is.
**Rationale:** Converting every single occurrence across the whole codebase — including internal error-handling strings never normally seen by a user — was judged disproportionate scope creep against a task that gave an explicit, bounded list of what must be converted. The boundary drawn here (headings/navigation/empty-states/banners: converted; incidental prose and error fallbacks: left alone) keeps the change reviewable and matches what the brief actually asked for.

## 2026-08-05 — Two-panel Settings restructure and user profile page

**Decision:** `SettingsPage.jsx` was split into a thin two-panel shell plus one component per category under a new `frontend/src/components/settings/` directory (`SettingsNav`, `GeneralSettings`, `TerminologySettings`, `SigningExportSettings`, `UsersSettings`, `ComingSoonSettings`, `DangerZoneSettings`). The extra `GET /settings` calls are inexpensive (a handful of rows, Admin-only, called only when that category is actually opened).

**Decision:** The "Categories" management link (previously a flat settings row) was placed inside the new **General** category, even though the task brief's category list doesn't mention category management at all.
**Rationale:** The brief enumerates what each new category should contain but never says what happens to the pre-existing "Manage categories" link — dropping it from the UI entirely would be a silent regression of existing, working functionality (`/settings/categories`, already Admin-gated and unaffected by this restructure). General was judged the least-bad fit among the eight given categories.

**Decision:** The **Users** category is not a "Coming soon" placeholder like AI & Extraction / Storage & Backup / Notifications / Danger Zone. It renders real content: the list of not-yet-approved registrations (`GET /auth/pending-users`) with a role dropdown and an **Approve** button (`POST /auth/approve-user/{id}`) — both endpoints already existed (see the 2026-08-04 auth build entry) but had no frontend consumer anywhere in the app before this task.
**Rationale:** The brief's own wording singles Users out — "link to user management" — distinct from the explicit "'Coming soon' message" instruction given to every other placeholder category, so treating it as a sixth placeholder would contradict the brief. Building a full user-management page (editing existing users' roles, deactivating accounts) was judged out of scope here — the task's own BACKEND section only asked for self-service `/auth/me/*` endpoints, nothing about managing *other* users — so this stays scoped to the one piece of already-built-but-unwired backend functionality (pending-user approval) that fits "user management" without inventing new endpoints mid-task.

**Decision:** Mobile behaviour (category list first, tap slides to a content panel with a back arrow) is implemented as a CSS-only sliding track — `.kt-settings-track` is a flex row at double width (`200%`) with the nav and content panels each pinned to 50%, translated via `transform: translateX(-50%)` when a `.show-content` class is present on the shell — rather than mounting/unmounting the two panels or animating with JS.
**Rationale:** Keeps the "smooth transition" requirement working with a single CSS transition and no extra state beyond the `mobileShowContent` boolean already needed to decide which panel to show; matches the project's established minimal-dependency, hand-rolled-CSS pattern (no animation library, same as everywhere else in the app).

**Decision:** `users.display_name` (`VARCHAR(150)`, nullable, migration `0021`) was added. `UserOut` now includes it, and every place a user's name is shown (Header, Profile page, the Users approval list is unaffected since it shows pending *registrations* which never have one yet) falls back to `username` when it's unset.
**Rationale:** The task brief's profile page explicitly needs an editable "display name" distinct from the immutable username, and no such column existed. Nullable because every existing user (including the seeded Superadmin) has none yet, and the UI's `user.display_name || user.username` fallback (`Header.jsx`, `ProfilePage.jsx`) means a blank value is never shown as literally blank.

**Decision:** `PUT /auth/me/profile` and `PUT /auth/me/password` (`backend/routers/auth.py`) both use the existing `get_current_user` dependency, not `require_admin` or `require_standard` — any authenticated, approved role (including Read Only) can change their own name, email, or password.
**Rationale:** These endpoints act only on the caller's own row (`user` from the dependency, never a client-supplied id), so there is no cross-user privilege question — restricting a Read Only account from managing its own login credentials would contradict every other "acts on my own account" flow in the app (e.g. `GET /auth/me` itself has no role gate).

**Decision:** `PUT /auth/me/profile` checks email uniqueness with `User.email == payload.email, User.id != user.id` (i.e. excluding the caller's own current row) before accepting the change, matching the pattern already used by `/auth/setup` and `/auth/register` for new-account email uniqueness.
**Rationale:** Without excluding the caller's own id, a user resubmitting their own unchanged email would incorrectly be told it's "already registered" — the constraint needs to mean "taken by *someone else*," not "already exists."

**Decision:** The DELETE order/table list in this task's brief includes `notifications`, but no such table exists anywhere in this codebase — `database-schema.md` documents one, but the main dashboard build (see that entry above, 2026-08-04) deliberately computes dashboard notifications live from other tables instead of building it. `perform_reset()` (`backend/services/system_reset_service.py`) simply has nothing to delete from and doesn't reference the table at all.
**Rationale:** Matches this log's established practice of treating a documented-but-never-built table as a no-op rather than inventing a migration for a table nothing else in the app reads or writes, purely to satisfy one line of this task's table list.

**Decision:** `DEFAULT_CATEGORIES` (the same 7 rows as migration `0003`) and `DEFAULT_SETTINGS` (the full set of rows seeded across migrations `0007`, `0014`, `0015`, `0018`, `0019`, `0020` — 12 keys in total) are duplicated as constants in `services/system_reset_service.py` rather than imported from the migration files themselves.
**Rationale:** A runtime reseed and a one-off migration-time seed are different operations that happen to want identical starting data; importing from `alembic/versions/` would couple runtime code to migration internals that are free to be squashed or rewritten later. Matches the precedent `services/settings_service.py`'s `TERMINOLOGY_DEFAULTS` already set for exactly this situation (its own comment: "Defaults match the seeded values in migration 0019 — used as the fallback... same pattern as `is_signing_enabled`").

**Decision:** Rate limiting (3 attempts/hour) is implemented by querying the `system_events` table itself — `recent_attempt_count()` counts `system_reset_success`/`system_reset_failed` rows for that `performed_by` in the trailing hour — rather than adding a rate-limiting library or any in-memory counter. A request rejected purely for being rate-limited is logged under a third, separate event type (`system_reset_rate_limited`) that is deliberately excluded from that count.
**Rationale:** Matches the project's established minimal-dependency convention (no new packages for something a query over data already being written can do), and reuses infrastructure the task already required (the permanent audit log) rather than adding a second, parallel tracking mechanism. Excluding `rate_limited` events from the count specifically prevents a locked-out caller from extending their own lockout by hammering the endpoint — each such request adds a new timestamp to the window only if it were counted, which would otherwise never let the window expire while attempts kept arriving. ## 2026-08-05 — Full-screen signing UI and coordinate-mapping fix

**Decision:** Root-caused the reported "coordinate mapping is broken" bug to `SigningPanel.jsx`'s canvas CSS, not to the backend. Every PDF page canvas was rendered at a fixed pdf.js resolution (`renderPdfPage(..., scale=1.1)`, i.e. `canvas.width`/`.height` in that native resolution) but then displayed with `.kt-sign-canvas { max-width: 100% }` — on any viewport narrower than that native resolution (which, at scale 1.1, was most of them), the browser shrank the canvas visually while the drag/percentage math still worked in the canvas's *native* pixel space. Pointer deltas (`e.clientX`/`e.clientY`, real screen pixels) were then applied 1:1 to that native-pixel space, so the box moved faster or slower than the cursor and visibly drifted from wherever the user actually dragged it. `backend/services/signing_service.py` and `InvoiceSignRequest` were already fully percentage-based and already used `page.rect` (confirmed directly with a throwaway `fitz` script: a page rotated 90° reports `page.rect` as `100×200` for a `200×100` mediabox, and `get_pixmap()` renders at that same rotated size) — so no backend change was needed for Part 2 of this task; the fix is entirely in how the frontend renders and measures the PDF.

**Decision:** `renderPdfPage` (`frontend/src/utils/pdf.js`) now takes a `targetWidth` (CSS pixels) instead of a fixed `scale`, renders the backing canvas at `targetWidth * devicePixelRatio` for crispness, but pins `canvas.style.width`/`.height` to the CSS-pixel size and returns that same CSS-pixel `{width, height}` to the caller. `SigningPanel` measures its own available width via a `ResizeObserver` on the scroll container and re-renders every page to fill exactly that width — the `max-width: 100%` CSS rule was removed entirely, since the canvas is now always rendered at the size it's displayed at, not shrunk into it after the fact. This is what makes the percentage math (and the box's on-screen position) match the visually rendered PDF at any viewport size, including live window resizes.
**Rationale:** Once the canvas's native resolution and its CSS-displayed size are the same number, `e.clientX`/`e.clientY`-based pointer deltas are already in the correct coordinate space with no scaling correction needed — the simplest fix available, and it also naturally makes the redesigned full-screen layout (PDF width now varies with viewport/toolbar-drawer state, not fixed) responsive without extra math.

**Decision:** `SigningPanel` was rewritten to render into a `createPortal(..., document.body)` full-screen overlay (`position: fixed; inset: 0; z-index: 1000`) instead of a two-column grid embedded inside `ReviewCard`/`InvoiceDetailPage`. **Rationale:** Directly implements this task's "takes over the full browser window... the rest of the app UI hidden" requirement. A portal to `document.body` is the simplest way to guarantee that coverage regardless of which page (`ReviewCard`'s upload flow, or `InvoiceDetailPage`'s standalone sign/re-sign flow) opened it, with no change needed to either page's own layout/z-index — consistent with the project's "no component library, plain browser APIs" pattern already established for the drag/resize logic itself.

## 2026-08-05 — Fix PDF.js canvas conflict in the signing panel

**Decision:** Root-caused the "Cannot use the same canvas during multiple render() operations" error to `SigningPanel.jsx`'s page-rendering effect (`renderAll`, keyed on `[numPages, containerWidth]`), not to the upload preview. That preview (`ReviewCard.jsx`) hasn't used pdf.js at all since the 2026-08-04 rotation-bug fix — it's a server-rendered `<img>` — so the two are already fully isolated; the conflict was entirely internal to `SigningPanel`. pdf.js tracks "is this canvas mid-render" in a single static `WeakSet` keyed by the canvas element (`InternalRenderTask.#canvasInUse`, confirmed directly by reading `pdf.mjs`) and throws exactly this error if a second `page.render()` targets a canvas still in that set. `renderAll` renders every page sequentially in a `for` loop, but its cleanup only flipped a local `cancelled` flag checked *after* the loop finished — it never called pdf.js's own `RenderTask.cancel()`, and the loop itself never checked `cancelled` between iterations. Once the PDF's pages laid out and the scroll container's vertical scrollbar appeared, `ResizeObserver` (watching that same container) fired again, `containerWidth` changed by a few pixels, and the effect re-ran — starting a second `renderAll` pass over the *same* `<canvas>` elements while the first pass was potentially still mid-render on a later page. That's the exact scenario the task brief described ("entering the signing flow after the upload preview"): the second pass is what actually threw, and it was reliably reproducible on first load of any PDF tall enough to trigger a scrollbar, not something upload-preview interference caused.
**Rationale:** Confirming the mechanism first (rather than guessing) is what showed the fix belonged entirely in `SigningPanel`'s own render lifecycle — no upload-preview isolation work was needed since none existed to begin with.

**Decision:** `renderPdfPage` (`frontend/src/utils/pdf.js`) no longer awaits `page.render(...).promise` internally — it returns `{ width, height, renderTask }` as soon as the render has *started*, handing the `RenderTask` back to the caller. `SigningPanel` now keeps one `RenderTask | null` per page index in a `renderTasksRef`, and before rendering into a given canvas it cancels whatever task is already tracked for that index (`prevTask.cancel()`) — synchronously, before the new `page.render()` call ever reaches pdf.js's `initializeGraphics()` (where the `WeakSet` check lives). The `renderAll` loop also now checks `cancelled` on every iteration (not just after the loop), and a `RenderingCancelledException` from an awaited `renderTask.promise` is treated as an expected, silent supersession rather than a real error (previously it would have surfaced as "Could not preview this PDF").
**Rationale:** This is the only sequencing that's actually safe against pdf.js's real (static, cross-document) reentrancy guard — a boolean "don't setState" flag was never going to prevent two `RenderTask`s from targeting one canvas, only cancelling the earlier one before the later one starts does that.

**Decision:** Each page's `<canvas>` is now keyed by `` `${docId}-${i}` `` (`docId` is a ref-backed counter bumped every time the `file` prop changes) instead of just the page index `i`, and the PDF-loading effect now proactively cancels all render tasks and destroys the previous `pdfRef.current` document at the *start* of its run (in addition to its cleanup), before bumping `docId`.
**Rationale:** Directly implements the task brief's "unique canvas key per render context" requirement, so that if `SigningPanel` were ever reused across documents without a full unmount (it currently isn't — see below), React would still tear down and recreate the canvas DOM nodes rather than handing a new document's renders the previous document's canvases. Belt-and-braces alongside the `RenderTask` cancellation, not a fix for a bug this app can currently hit.

**Not changed:** The "switching pages via the page selector" part of the task brief doesn't apply literally — per the 2026-08-05 full-screen signing UI entry above, all pages are already rendered up front (so the signature box can be dragged to any of them across one continuous scroll), and the page selector only calls `scrollTo()`, it never triggers a new render. Re-architecting that into per-page lazy rendering would be a much larger change than this bug needs and would regress the drag-across-pages UX that redesign deliberately built. Similarly, no code changes were needed for "upload preview isolation" (see above) or "revoke object URLs on close" — `SigningPanel` never creates a long-lived object URL for the PDF itself (it reads `file` via `arrayBuffer()`); the one object URL it does create, for the downloaded signed PDF, was already synchronously revoked right after triggering the download, before and after this fix.

Writing it at the true end of authentication for each path — rather than, say, always in `/auth/login` — is what keeps "last login" meaning what it says: a Standard/Admin user who enters the right password but fails or abandons the MFA step never got a last-login bump for a login that didn't actually complete.

**Decision:** `users.is_active` is checked in three places, not one: `POST /auth/login` (blocks the password step), `POST /auth/verify-mfa` (re-checked against the DB row, not trusted from the temp token, in case an Admin deactivates the account in the up-to-5-minute gap between password and MFA), and `get_current_user` (`utils/deps.py`, so an already-issued 8-hour access token stops working immediately once an Admin deactivates the session's owner, rather than staying valid until it naturally expires).
**Rationale:** The task brief's literal requirement is only "reject inactive users with a clear message" at login, but checking solely at login leaves a large hole: an Admin deactivating a user they believe is locked out immediately (e.g. a compromised or departing account) would have no actual effect on that user's already-open session for up to 8 hours. Re-checking in `get_current_user` — the single dependency every authenticated endpoint already goes through — closes that gap for free, consistent with the project's existing pattern of the backend being the real source of truth rather than trusting a token's claims alone (see the signing-enabled re-check in the 2026-08-04 PDF signing entry).

**Decision:** `PUT /auth/me/force-password-change` is a new, separate endpoint from the existing `PUT /auth/me/password` — it accepts only `new_password` (no `current_password` field), whereas the existing endpoint still requires and verifies the current one.
**Rationale:** The task brief's Change Password page only collects "new password and confirm password," with no current-password field — and by the time a user reaches it, they've just authenticated with their current (temporary) password seconds earlier via a real login (password + MFA), so re-asking for it would be redundant friction, not extra security. The endpoint is only reachable with a valid access token at all, which is exactly the same authentication bar the existing self-service endpoint already relies on beneath its current-password check. Both endpoints now clear `must_change_password` on success, not just the new one — so a user who still has the flag set (e.g. they closed the tab mid-flow and came back through a different route) is unblocked by any successful password change, not only the forced-change path.

**Decision:** A `DELETE /auth/reject-user/{id}` endpoint was added, not in this task's original BACKEND endpoint list, and it hard-deletes the row rather than soft-deleting it. It refuses (`400`) if the target is already approved.
**Rationale:** The FRONTEND section explicitly requires a "Reject button with confirmation" on the Pending Approval tab, but no backend support for rejection existed anywhere (only `POST /auth/approve-user/{id}`) — the frontend requirement had no endpoint to call. Hard-deleting (rather than following the soft-delete/deactivate pattern used for invoices, categories, and now approved users) is safe specifically because an unapproved registration is, by definition, a row nothing else in the system references yet — no invoice, contribution, or project can have been created by a user who was never allowed to log in. The `already approved` guard keeps this endpoint from ever being usable as a backdoor way to hard-delete a real, approved account, which stays governed by deactivate/reactivate only.

**Decision:** `PUT /auth/users/{id}/role`, `PUT /auth/users/{id}/deactivate`, and `POST /auth/users/{id}/reset-password` all share one guard (`_reject_action_on_self_or_superadmin`) that blocks the action if the target is the acting Admin's own account or has the `superadmin` role — including for reset-password, which the task brief's BACKEND section didn't explicitly restrict.
**Rationale:** The brief's FRONTEND section states plainly, for the Actions column as a whole, "Cannot action own account or Superadmin account" — covering reset password alongside deactivate and role change, not just the two the BACKEND section happened to spell out per-endpoint. Enforcing it server-side too (not just hiding the buttons in the UI) matches the project's established pattern of the backend being the real authority rather than trusting the frontend to withhold a button — the same reasoning as the `is_active` re-check above and the signing-enabled re-check precedent.

**Decision:** `PUT /auth/users/{id}/reactivate` has no target restriction beyond `require_admin` — an Admin can reactivate any inactive user, including (hypothetically) their own account or one that used to be Superadmin.
**Rationale:** Reactivate is a strictly safe, reversible action being applied to an account that's currently *locked out* — there's no privilege to protect against here the way there is with role changes or deactivation. In practice the Superadmin account can never reach `is_active = false` at all (it's excluded from deactivation by the shared guard above), so the "reactivate a Superadmin" case can't actually occur; leaving no restriction was simpler than adding a defensive check for a state the system never produces.

**Decision:** The reset-password temporary password is 8 random characters drawn from `string.ascii_letters + string.digits` via Python's `secrets.choice` (not `random`), matching the task brief's literal "8 characters, random, alphanumeric" spec exactly rather than adding extra complexity requirements (a symbol, guaranteed-mixed-case, etc.) the brief didn't ask for.
**Rationale:** `secrets` (not `random`) is Python's cryptographically-secure choice for anything credential-shaped — the existing codebase already uses it nowhere else for this purpose since this is the first server-generated credential, but it's the standard-library equivalent of the bcrypt/Fernet care already taken with passwords and MFA secrets elsewhere in this app. Un-hashed, the temporary password is only ever held in memory for the single response that returns it to the Admin — it's never logged or stored in plaintext (`user.password_hash = hash_password(temporary_password)`), same as any user-chosen password.

**Decision:** `GET /auth/users` returns every user regardless of `approved` status (including pending registrations), ordered by username. The frontend's Active Users tab filters the response to `approved === true` client-side rather than the backend filtering server-side; the existing `GET /auth/pending-users` (unchanged) continues to back the Pending Approval tab.
**Rationale:** The task brief's own field list for this endpoint includes `approved`, which would be a pointless field to return if the endpoint only ever returned already-approved rows. Filtering client-side avoids adding a query parameter or a second backend endpoint for what is, from the API's point of view, just "list all users" — the two tabs are a frontend presentation split, not two different data sets.

**Decision:** `RequireAuth` and `RequireAdmin` (`frontend/src/components/RouteGuards.jsx`) both now redirect to `/change-password` whenever `user.must_change_password` is true and the current path isn't already `/change-password` itself; `DefaultRedirect`'s catch-all does the same. `/change-password` sits outside the `Layout`-wrapped route group (alongside `/mfa` and `/pending-approval`), so a user stuck there sees no sidebar/header navigation to click away through, and the two guards mean typing any other URL directly bounces straight back.
**Rationale:** Directly implements "User cannot navigate away from this page until password is changed." Putting the check in both guards (rather than just one, or a single new `RequireNoForcedChange` wrapper around everything) was necessary because `/settings` and its sub-pages are gated by `RequireAdmin`, not `RequireAuth` — an Admin whose own password was reset by the Superadmin would otherwise be able to reach Settings while every other page redirected them.

**Decision:** The Active Users table's `<table>` is wrapped in the existing `.kt-table-scroll` class (already used by Contributions' monthly summary table and originally introduced for it), rather than left unwrapped like `InvoicesPage`'s narrower table.
**Rationale:** Caught during Playwright testing at a 1280px viewport: with seven columns (User, Email, Role, Created, Last login, Status, Actions) the table is wide enough that, unwrapped, its right-hand Actions column ran off the edge of the page with no way to reach it — confirmed via `document.body.scrollWidth` before the fix. Wrapping it in the same horizontal-scroll container already established for Contributions' equally-wide table fixes this without introducing a new pattern.

## 2026-08-05 — Pagination and CSV/PDF export across all list views

**Decision:** A single shared pair of backend helpers — `paginate()` (`backend/utils/pagination.py`) and `csv_response()` (`backend/utils/csv_export.py`) — plus a generic `PaginatedResponse[T]` Pydantic model (`models/schemas.py`, using `typing.Generic`) back every paginated list endpoint (`GET /invoices`, `/contributions`, `/reconciliation`, `/reports`, `/auth/users`). `per_page <= 0` is the sentinel the frontend's "All" per-page option sends, meaning "no limit" — the response then reports a single page containing every matching record, rather than the endpoint needing a second, differently-shaped response type for that case.
**Rationale:** All five endpoints needed identical page/offset math and an identical `{data, pagination}` envelope; a shared generic avoided five near-identical copies of the same pagination arithmetic and kept the response shape (task brief's exact field list — `page`, `per_page`, `total_records`, `total_pages`, `has_next`, `has_previous`) consistent everywhere. Treating "All" as a real, always-single-page response (rather than a client-side "fetch everything with a huge per_page number") means the frontend's `PaginationBar` never needs a separate code path for it.

**Decision:** A second shared backend helper, `generate_table_export_pdf()` (`backend/services/export_pdf_service.py`), builds every list view's branded PDF export (Invoices, Contributions, Reconciliation). It reuses the exact brand colours already defined in `services/pdf_report_service.py` (the AI-report PDF builder) and the same header-rule/footer-rule visual style, but is a single striped-table document rather than a multi-section report. No logo image file exists anywhere in the repo — `frontend/src/components/Logo.jsx` is inline SVG — so the header logo is hand-drawn with ReportLab canvas primitives (`rect`/`circle`) mirroring that SVG's three shapes directly, the same "redraw the brand mark in the target format" approach already established for `pdf_report_service.py` rather than adding a new static logo asset just for exports.
**Rationale:** Keeps every export PDF visually consistent with the app's one existing PDF output (generated reports) without duplicating brand-colour constants or footer-drawing code a third and fourth time. Landscape A4 was used (rather than the reports' portrait A4) since export tables have more columns than the report's own summary tables and needed the extra width to stay readable.

**Decision:** `InvoicesPage`'s existing "Signed" filter — previously a client-side `.filter()` applied to the *entire* unpaginated invoice array after fetching it — was promoted to a real backend query param (`signed=signed|unsigned` on `GET /invoices` and both `/invoices/export/*` endpoints), with the exact same semantics it already had (an unreviewed invoice counts as neither signed nor unsigned, so "unsigned" means `reviewed AND NOT signed`, not just `NOT signed`).
**Rationale:** A client-side post-filter only works when the full list is in memory at once; once `/invoices` returns one page at a time, filtering client-side would silently show fewer than `per_page` rows (or an empty page) whenever a page happened to contain few/no matching rows, and CSV/PDF export (which hits the backend directly, never the paginated frontend state) had no way to honour the filter at all. Moving it server-side, with identical semantics, was the only way to keep "filters work correctly across pages" and "export respects all currently active filters" both true for this filter specifically.

**Decision:** `GET /auth/users` gained an `approved: bool | None` query filter, not in the task brief's literal param list (`page`/`per_page` only).
**Rationale:** `ActiveUsersTab` previously fetched *every* user and filtered to `approved === true` client-side. Under server-side pagination that has the same problem as the Invoices "signed" filter above — a page of 25 users containing several pending registrations would show fewer than 25 approved rows and a wrong "Showing X–Y of Z" count. Filtering `approved=true` server-side keeps the tab's pagination numbers honest; `PendingApprovalTab` is unaffected since it already uses the separate, un-paginated `GET /auth/pending-users` endpoint.

**Decision:** `ContributionsPage` and `ReconciliationPage` don't have a single obvious "the list" the way Invoices/Reports/Users do. `ContributionsPage` paginates only its existing "All entries" list (the fixed 12-row "Monthly summary" table above it is untouched — it's a summary, not a paginated record set). `ReconciliationPage` gained a brand-new "Reconciliation history" table below the existing 12-tile month picker, backed by `GET /reconciliation` with no `financial_year_id` filter (i.e. every reconciled month across every financial year, most recent first) — the month-tile picker itself (which only ever shows the current FY's 12 months and has no "list" to paginate) was left exactly as it was.
**Rationale:** The month-tile UI is a *picker*, not a browsable record list, and forcing pagination onto 12 fixed tiles would add UI with nothing meaningful to page through. A genuine cross-year, most-recent-first history table is what the task's export requirement ("exports everything matching current filters") actually needed a target for, since the tile picker itself has no concept of "matching filters" to export.

**Decision:** The default sort for `GET /contributions` and `GET /reconciliation` changed from ascending (by month) to descending (most recent first), per the task's explicit "Sorting should be consistent across pages (default: most recent first)" requirement. Checked first that nothing relied on the old ascending order: `ContributionsPage`'s "All entries" list has no ordering dependency (each row is independently editable), and `reconciliationApi.list()` had no frontend caller at all before this task (`ReconciliationPage` only ever used the per-month `GET /reconciliation/{year}/{month}` lookups) — confirmed by grep before changing it.
**Rationale:** A silent ordering change is only safe when nothing depends on the old order; both were verified un-depended-upon rather than assumed safe.

**Decision:** Page/per-page state (`frontend/src/hooks/usePaginationState.js`, shared by all five list views) treats the URL's `page`/`per_page` query params as the single source of truth — read directly from `useSearchParams()` on every render, not mirrored into separate `useState` — while a per-list localStorage key (`keeptrack-per-page-{key}`) remembers the last per-page choice across visits and seeds a fresh visit's URL if it arrives without one.
**Rationale:** Mirroring URL params into local state risks the two drifting apart, which is exactly what would break "browser back/forward should work correctly" — the browser changing the URL on back/forward only updates state automatically if the state *is* the URL, not a copy of it taken once on mount.

## 2026-08-05 — Audit logging, error logging, log viewer, and automatic retention

**Decision:** `audit_log` and `audit_log_archive` are two separate, fully duplicated SQLAlchemy model classes (`backend/models/audit_log.py`) rather than a shared mixin or a single table with an `archived` flag. Their Python attribute for the `metadata` column is `extra_metadata` (mapped via `Column("metadata", JSONB, ...)`), not `metadata`, since SQLAlchemy's declarative `Base` reserves `metadata` for its own `MetaData` object.
**Rationale:** Matches this project's established preference for explicit duplication over cross-cutting abstraction for tables (e.g. `DEFAULT_CATEGORIES`/`DEFAULT_SETTINGS` duplicated in `services/system_reset_service.py` rather than imported from their migrations). A single flagged table would also make "never purged" harder to reason about — a stray `UPDATE` could silently un-archive a permanent record. The `extra_metadata` attribute rename is a hard SQLAlchemy constraint, not a style choice — attempting `metadata = Column(...)` raises at class-definition time.

**Decision:** This app has only one review/confirm step for invoices (`POST /invoices/{id}/confirm`, which sets `reviewed = true`) — there is no separate "confirmed" state in the data model distinct from "reviewed." That single endpoint logs `invoice.reviewed` only; `invoice.confirmed` (also listed in the task brief) is never emitted.
**Rationale:** Emitting both for the one action that exists would just be two audit rows for a single click, with no second action anywhere in the app that `invoice.confirmed` could distinctly describe. `invoice.reviewed` was chosen over `invoice.confirmed` since it matches the column name (`invoices.reviewed`) the rest of the codebase already uses for this state.

**Decision:** `POST /invoices/{id}/sign` checks whether the invoice was already `signed` before the call and logs `invoice.signed` (first signature) or `invoice.resigned` (already-signed invoice signed again) accordingly, rather than the endpoint or frontend needing to say which one it means.
**Rationale:** Directly implements the task brief's separate `invoice.signed`/`invoice.resigned` action types using a signal the backend already has (the invoice row's own `signed` flag, read before it's overwritten) — no new column or request field needed.

**Decision:** A new `POST /auth/logout` endpoint was added (not in this task's brief or any earlier one), called best-effort by `AuthContext.logout()` before it clears the local token. It does nothing but write a `user.logout` audit entry.
**Rationale:** Login in this app is stateless JWT — there was never a server-side session to end, so nothing previously called the backend on logout. The task brief lists `user.logout` as a required audit action type; without a server round-trip at logout, there is no point in the app where that action could be observed and logged. The call is fire-and-forget (`.catch(() => {})`) so a network hiccup can never block a user from actually logging out client-side.

**Decision:** Login/MFA failures and unapproved/deactivated login attempts are logged to **both** `audit_log` (`user.login_failed`, `user.mfa_failed` — the security-relevant "who tried what") and `error_log` (`source='auth'`, `severity='warning'` — the operational "something failed") — two entries for the same event, not one or the other.
**Rationale:** The task brief's error-logging section explicitly names `'auth'` as an example `source` value, and separately requires `user.login_failed`/`user.mfa_failed` as audit action types — read literally, both logs are meant to carry this event. They serve different audiences in the new Logs viewer (the Audit tab's security trail vs. the Error tab's operational feed), so keeping both was treated as the literal, intended requirement rather than an accidental duplication to collapse.

**Decision:** `services/ai_service.py`'s `extract_invoice_data` and `generate_report_summary` (and their private `_parse_*_response` helpers) gained an optional `db: Session | None = None` parameter, threaded through from `routers/invoices.py`'s upload endpoint and `routers/reports.py`'s generate endpoint. When given, failures (missing API key, API error, unparsable JSON) are also recorded to `error_log` (`source='ai_extraction'` / `source='ai_report_summary'`) in addition to the existing `logger.warning`/`logger.exception` calls; when omitted, behaviour is unchanged from before this task.
**Rationale:** Both functions already had a well-established "degrade gracefully, never raise" contract (see the 2026-08-04 invoice upload entry) — the task brief's requirement to log these failures to `error_log` needed a DB session to write with, and making the parameter optional (rather than required) meant no other, unrelated caller of these functions had to be touched or could break.

**Decision:** `audit_log.archived` is written directly into `audit_log_archive` by `services/maintenance_service.archive_old_audit_logs()` — never into `audit_log` via `audit_service.log_action()` like every other audit entry in the app.
**Rationale:** The task brief's own wording is explicit: "Log the action to `audit_log_archive` itself." It's also the only placement that makes sense structurally — if the archive event were logged to the *active* table, it would itself become an ordinary 90-day-old row eventually swept into the archive by some *future* archive run, which would be a strange, indirect way to record "an archive run happened."

**Decision:** "Send an Admin notification after completion" (the quarterly archive job) is implemented as a live `GET /dashboard/notifications` entry — shown to Admin/Superadmin only, for 24 hours after the most recent `audit_log.archived` event — rather than a new stored/emailed notification. It reuses that event's own `description` text verbatim (already contains the count and date) instead of recomputing a message. The existing `notifications` DB table (documented in database-schema.md, never actually built — see the 2026-08-04 main dashboard build entry) is still not used.
**Rationale:** Every dashboard notification in this app is already computed live from other tables rather than stored as its own row (balance warnings, unreviewed-invoice counts, unsigned-invoice counts) — adding a stored notification here would be the first of its kind and a second, inconsistent pattern for "tell the Admin something happened." Reading the last archive event's own row for both the "did this run recently" check and the message text keeps the notification from ever silently disagreeing with the audit trail it's describing.

**Decision:** The critical-error dashboard notification and the audit-archived notification are both gated to `user.role in ("admin", "superadmin")` inside `GET /dashboard/notifications`, rather than left visible to every role like the rest of that endpoint's notifications.
**Rationale:** Both link to Settings → Logs, and `/settings` is entirely `RequireAdmin`-gated on the frontend — a Standard or Read Only user shown either banner would click through to a page they're immediately redirected away from. Scoping the notification itself to the roles that can actually act on it avoids a dead-end banner.

**Decision:** `POST /logs/audit/archive` (a manual "Archive now" trigger) and the `next_error_cleanup_run` field on `GET /logs/status` were both added beyond the task brief's literal endpoint/field lists (which specified GET-only endpoints, and only `next_archive_run`).
**Rationale:** The brief's own FRONTEND section requires an "Archive now" button that "triggers manual archive immediately" — nothing in the literal backend list could serve that button, so the gap had to be filled the same way earlier tasks in this log have filled similar gaps (e.g. `GET /auth/setup-status`, `GET /financial-years/current`). `next_error_cleanup_run` was needed because the FRONTEND section's Error Log tab explicitly asks for "Last cleanup: [date] — Next cleanup: [estimated date]," which the literal backend field list had no field for.

**Decision:** The 90-day retention scheduler (`services/maintenance_service.py`) is a single `threading.Thread(daemon=True)` running `time.sleep(90 days)` in a loop, not APScheduler. `main.py`'s startup hook calls `run_maintenance_once()` synchronously once (so a fresh container always has an up-to-date log immediately) and *then* starts the thread, whose loop sleeps first — so the two can never race to both run at t=0.
**Rationale:** The task brief explicitly offered this as the preferred option ("keep it lightweight, no additional infrastructure needed") for a job that only needs to fire a handful of times a year. Adding APScheduler (a new dependency, with its own job-store/misfire semantics to configure) for a single 90-day interval would be more machinery than the requirement warrants, and would break this project's established minimal-dependency convention (plain `fetch`/XHR over axios, no charting library, no DnD library — see multiple earlier entries in this log).

**Decision:** `app.exception_handler(Exception)` in `main.py` catches and logs to `error_log` (`severity='critical'`, `source='unhandled'`) only exceptions that escape every router's own handling — FastAPI's built-in `HTTPException` handler (registered by default) still takes priority for any deliberately-raised `HTTPException`, since Starlette's exception-handler lookup walks the exception's MRO and matches the most specific registered handler first.
**Rationale:** The task brief asks for "unhandled exceptions," meaning bugs, not the hundreds of intentional `HTTPException(status.HTTP_4xx, "...")` calls already throughout the routers — logging every deliberate 404/400/403 as a "critical unhandled exception" would flood the error log with noise and misrepresent normal, expected request failures as system errors.

**Decision:** `system.reset` is now logged twice on a successful reset — once to `system_events` (via the pre-existing `log_reset_event`, which backs the reset endpoint's own rate limiting and is deliberately exempt from the reset it records) and once to `audit_log` (via `audit_service.log_action`, new in this task, backing the new Logs viewer) — both written, like the existing `system_events` row, *before* `perform_reset()` runs.
**Rationale:** `system_events` predates this task and has its own specific job (rate-limiting reset attempts) documented in the 2026-08-05 system-events entry above; repurposing it as the audit trail for the new Logs viewer would couple two unrelated concerns. Writing both, at the same "before anything is deleted" point, satisfies the brief's "always logged, even before data is wiped" requirement without disturbing the existing rate-limit mechanism. `audit_log`/`audit_log_archive` are not among the tables `perform_reset()` clears, so both survive a reset intact, same as `system_events` already did.

**Decision:** `PUT /settings/{key}`, `PUT /settings/terminology`, and `DELETE /settings/{key}` (clear) all now log `settings.changed` with `metadata: {key, before, after}` — including `PUT /settings/terminology`, which logs one `settings.changed` entry per changed `term_*` field rather than one combined entry for the whole request.
**Rationale:** The task brief specifies `settings.changed` should "include key, before value, after value in metadata" — a single field-per-key shape that a combined multi-field entry couldn't represent cleanly. Per-field entries also match how `PUT /settings/{key}` (the single-setting endpoint) already has to work, so both endpoints produce audit rows with the same shape.

## 2026-08-05 — File storage configuration and full backup/restore build

**Decision:** The new `storage_path` setting defaults to `"/data"`, not the `/app/storage` named in the task brief, and becomes the single root all three file types live under: `{storage_path}/invoices/original/`, `{storage_path}/invoices/signed/`, `{storage_path}/reports/`. The three previously-separate, env-only config fields (`invoice_storage_path`, `signed_invoice_storage_path`, `report_storage_path`) were removed from `config.py` and `.env.example` entirely; `services/storage_service.py` now resolves all three paths from the DB setting (falling back to `"/data"` if the row is somehow missing) instead of from `config.py`.
**Rationale:** `/data` is the parent of the `invoice_storage`/`report_storage` Docker volumes already mounted at `/data/invoices` and `/data/reports` (`docker-compose.yml`), so `{storage_path}/invoices/original` etc. resolve to *exactly* the same physical paths those three env vars already pointed at — a fresh deployment's default doesn't move a single existing file. An unmounted `/app/storage` path would not persist across container restarts, the same reasoning behind every earlier storage-path deviation in this log (original/signed invoice storage, report storage). Collapsing three static paths into one DB-backed root is also what makes `PUT /storage/path` (changing the path at runtime) meaningful at all — env vars can't be changed by an in-app action.

**Decision:** `services/storage_service.save_invoice_pdf`, `save_report_pdf`, and `services/signing_service.sign_invoice_pdf` all gained a required `db: Session` parameter, and every call site (`routers/invoices.py`, `routers/reports.py`) was updated to pass it through.
**Rationale:** Once file paths are resolved from a DB setting rather than a static config value, every function that decides *where* to write a file needs a session to read that setting with — otherwise changing `storage_path` at runtime would only affect *already-uploaded* files (via the move endpoint) and not where the *next* upload goes, immediately reintroducing the "files scattered across two locations" problem the feature exists to solve.

**Decision:** `storage_service.move_storage_root` (used by `PUT /storage/path` with `move_files=true`) moves the individual entries *inside* `{root}/invoices` and `{root}/reports`, not those two directories themselves.
**Rationale:** Confirmed directly against the running dev stack: an earlier version called `shutil.move(old_root/invoices, new_root/invoices)` as a single operation. `old_root/invoices` is a Docker volume mount point in the default deployment, and renaming a mount point fails with "Device or resource busy" — but only *after* `shutil.move`'s internal fallback (`copytree` then `rmtree` when `os.rename` raises `OSError`) had already deleted every file inside it via `rmtree`, which removes a directory's contents before the final `rmdir` on the directory itself fails. The first real test of this endpoint silently deleted 14 files with a "success... wait, error" response, recovered only because a backup taken moments earlier still had copies. The fix (move each entry inside "invoices"/"reports" individually, leaving the mount point itself untouched) exactly mirrors the already-documented reasoning in `system_reset_service._clear_directory_contents` for the same class of problem.

**Decision:** `services/backup_service._stage_existing_storage_aside` (the "keep the pre-restore files around in case the restore fails" step of `POST /storage/restore`) has the identical fix applied for the identical reason — it stages aside the *contents* of `storage_root/invoices` and `storage_root/reports`, never `storage_root` itself.
**Rationale:** Same root cause as `move_storage_root` above, caught by the same live test: the first version staged `storage_root` (`/data`) as a single unit, which — since `/data/invoices` and `/data/reports` are mount points nested *inside* `/data` — triggered the identical `rename`-fails/`rmtree`-partially-succeeds data loss, this time during a restore rather than a path change. Recovered from a backup a second time. Both functions now share the same "operate one level below the mount points" pattern.

**Decision:** `POST /storage/restore` explicitly closes its own `db: Session` (the one FastAPI already opened via `Depends(get_db)` to load the authenticated Superadmin) immediately after verifying the Superadmin's password, before running `pg_dump`'s `--clean` restore.
**Rationale:** Confirmed directly: without this, the request-scoped session used to authenticate the request stays open (FastAPI doesn't close a `Depends(get_db)` session until the whole endpoint function returns) and sits "idle in transaction" for the entire restore. `pg_dump --clean`'s `DROP TABLE` statements then block indefinitely waiting for a lock that connection is implicitly holding, hanging the restore forever — the first live test of this endpoint hung for over two minutes until the blocking connection was killed by hand via `pg_terminate_backend`. Closing the session explicitly (rather than, say, refactoring the whole restore to run outside a request-scoped dependency chain) was the minimal fix once the actual cause was found.

**Decision:** `pg_dump`/`psql` (not a Python-side dump/restore) do the actual database backup and restore, invoked via `subprocess` against `DATABASE_URL` directly (which `pg_dump`/`psql` both accept as a connection URI). The dump uses `--clean --if-exists`; the restore uses `psql --single-transaction --variable=ON_ERROR_STOP=1`. `backend/Dockerfile` now installs `postgresql-client-16` from the PGDG apt repository (not Debian's own `postgresql-client` package, whose bundled version can trail the server's) to match the `postgres:16-alpine` server in `docker-compose.yml`.
**Rationale:** The task brief explicitly asks for "PostgreSQL database dump (pg_dump) — complete dump including all tables, users, settings, everything" and "Restore database from pg_dump," which a hand-rolled per-table Python export/import wouldn't really be. `--clean --if-exists` makes the dump self-contained (it drops and recreates every object, so restoring into a non-empty database — the normal case — just works, no separate `dropdb` step). `--single-transaction` makes the *restore* atomic: any single statement failing rolls back everything, so a failed restore always leaves the database exactly as it was rather than half-replaced. Verified live: after the session-close fix above, a real restore against a real backup completed in well under a second.

**Decision:** `jwt_invalidate_before`, a new settings-table key (not part of the task brief's endpoint/schema list), is what "force all users to re-login (invalidate all JWT tokens)" is built on. `POST /storage/restore` stamps it with the restore's completion time; `utils/deps.get_current_user` rejects any token whose `iat` claim is earlier than that timestamp. When comparing, `jwt_invalidate_before` is floored to whole seconds before the comparison.
**Rationale:** Keep Track's JWTs are stateless (no per-user session table to revoke rows from), so there was no existing mechanism for "every token issued before now stops working" — a single settings-table timestamp, checked on every authenticated request (the same "just query it, no caching" pattern `is_signing_enabled` and every other settings-service lookup already uses), is the smallest addition that provides it. The flooring matters and was not optional: a JWT's `iat` only has whole-second resolution (python-jose drops the fractional part when encoding a token), but the invalidation timestamp was originally stored with microsecond precision — comparing them unfloored meant a login happening in the *same wall-clock second* as the restore (a near-certainty for the Superadmin logging back in immediately after, as the UI's own "Everyone, including you, must log in again" message invites) had an `iat` that floored to *before* the precise invalidation instant, and was wrongly rejected. Confirmed directly: the first end-to-end restore test locked the Superadmin out of the system they had just successfully restored, with no way back in except a second restore. Flooring both sides trades a theoretical ≤1-second window where a token issued in the same second as the restore could still work, for the far more important guarantee that a *fresh* login immediately afterwards always does.

**Decision:** `require_superadmin` (Superadmin only — `utils/deps.py`) was added alongside the existing `require_admin`/`require_standard`, following the exact shape of both.
**Rationale:** `POST /storage/restore` and `POST /storage/restore/preview` are the first endpoints in the app to need "Superadmin, not just Admin" as a *dependency-level* gate (the only precedent, `POST /system/reset`, checks `user.role` by hand inside the function body instead). A named dependency is more consistent with how every other role gate in the app already works.

**Decision:** `POST /storage/restore/preview` (Superadmin, multipart upload) and `GET /storage/backup/{filename}/download` / `DELETE /storage/backup/{filename}` were added beyond the task brief's literal endpoint list.
**Rationale:** Same pattern as several earlier additions in this log (`GET /auth/setup-status`, `GET /financial-years/current`, `POST /logs/audit/archive`). The brief's own FRONTEND section requires showing a manifest preview *before* restoring and requires per-backup Download/Delete buttons in Backup History — none of those have anything to call without these three endpoints, since the brief's literal list only included `POST /storage/restore` itself and `GET /storage/backup` (list). `restore/preview` re-validates the zip (checksum included) independently rather than trusting a client-supplied manifest, so a stale or tampered preview can't influence what the real restore endpoint does.

**Decision:** The restore preview's Superadmin-mismatch warning compares the backup's manifest `env.superadmin_username` snapshot (the *source* system's own `SUPERADMIN_USERNAME` at backup time) against this installation's `SUPERADMIN_USERNAME`, rather than inspecting the restored database directly.
**Rationale:** The preview endpoint deliberately never touches the database or the storage path — it only opens the zip and reads the manifest — so there is no "restored database" to inspect yet at preview time. `ensure_superadmin()` (run on every backend startup) keeps a system's actual Superadmin row's username in sync with its own `SUPERADMIN_USERNAME` env var, which is exactly what makes the manifest's env snapshot a reliable stand-in without needing to parse the SQL dump just to render a preview. The *real* restore endpoint's post-restore warning, by contrast, does check the actual restored `users` table — the two checks use different data because they run at different points in the two-step flow, but arrive at the same answer.

**Decision:** Checksum verification (`services/backup_service.validate_backup_zip`) runs *before* any part of a restore begins — both as the first step of the preview endpoint and as the first step of the real restore — rather than only after the database and files have been replaced, as a literal reading of the task brief's step ordering ("restore database → restore files → verify checksums") would suggest.
**Rationale:** Verifying a zip's integrity *after* you've already replaced the live database with its (possibly corrupted) contents defeats the purpose of checksumming at all — by the time you'd discover the corruption, the damage is already done and the single-transaction safety net has already committed. Failing fast on a bad zip, before touching anything, is strictly safer and was judged to matter more than matching the brief's literal step order; the brief's intent (verify the backup is genuine before trusting it) is still fully met.

**Decision:** "Send an Admin notification on success and failure" (scheduled backups) is implemented as an `audit_log` entry (`backup.created`) on success and an `error_log` entry (`critical`, `source='scheduled_backup'`) on failure — the same two places every other background job's outcome in this app already surfaces to Admins (see the 90-day retention scheduler's own notification handling above) — rather than a new notification channel.
**Rationale:** Keep Track has no outbound email/push capability anywhere in the app; Settings → Logs is the established, and only, place Admins already check for "did something happen in the background." Building a second, bespoke notification mechanism for just this one feature would be inconsistent with the retention scheduler's identical requirement, handled the identical way, earlier in this same build history.

**Decision:** `should_run_scheduled_backup` treats *any* backup (manual or scheduled) recorded in `last_backup_date` as satisfying "already backed up today," and the backup-schedule background thread checks every 5 minutes (not once a day) for whether 2am (UTC) has passed.
**Rationale:** A single shared `last_backup_date`/`last_backup_size` pair (as the task brief's DATABASE section specifies — not separate manual/scheduled fields) means a manual backup taken earlier the same day a scheduled one is due is a reasonable substitute, not a gap to fill twice. Checking every 5 minutes, rather than trying to fire exactly once at 2am, means a due backup still runs within a few minutes even if the app was mid-restart (or briefly down) exactly at 2am — at the cost of needing the same-day guard to prevent re-firing on every check within that hour, which `last_backup_date` already provides for free.

**Not addressed in this pass:** if an Admin configures `backup_path` to a location *inside* `storage_path` (e.g. `{storage_path}/backups`), a scheduled backup's own zip file would itself get walked and included in the *next* backup's file listing, growing without bound. `docs/storage-and-backup.md` recommends against nesting them but nothing in the backend currently prevents or warns about it.

## 2026-08-05 — Multi-provider AI configuration build

**Decision:** `backend/services/ai_provider_service.py` is a single new module that both stores/resolves AI configuration (reading `ai_provider`/`ai_model`/`ai_endpoint_url`/`ai_enabled`/`ai_api_key` from `settings`) and implements the actual per-provider calls, replacing the direct Anthropic SDK calls that used to live in `services/ai_service.py`. `ai_service.py` now holds only `check_duplicate` (an ordinary DB query, not an AI call); `routers/invoices.py` and `routers/reports.py` import `extract_invoice_data`/`generate_report_summary` from the new module instead.
**Rationale:** The task explicitly asked for both "a unified AI service that abstracts the provider" and for the existing call sites to be updated to use it — collapsing config-resolution and provider-dispatch into one module (rather than splitting them) keeps the "how is AI currently configured, and what does calling it look like" logic in one place, which matters because every entry point (extraction, report summaries, the test-connection endpoint) needs to re-derive the same config → credentials → dispatch chain.

**Decision:** Of the seven providers, only Anthropic is given the PDF natively (as a `document` content block, exactly as `ai_service.py` already did). Every other provider (OpenAI, Google, xAI, Mistral, Cohere, Ollama, Custom) receives the PDF as plain text, extracted with PyMuPDF (`fitz`, already a project dependency for preview rendering) and capped at 15,000 characters.
**Rationale:** Seven different SDKs have seven different (and not-directly-comparable) multimodal/file-upload APIs; implementing native PDF/image input for all of them was judged out of proportion to this task's scope. Extracted text is the one input shape that works identically across every provider's plain chat-completion endpoint. This does mean non-Anthropic providers can't read a purely image-based (scanned, no text layer) invoice — considered an acceptable, documented limitation given Anthropic remains the recommended/default provider and keeps its existing higher-fidelity path.

**Decision:** API key resolution has exactly one priority chain per the task brief (database setting → environment variable → none), backed by a **single** `ai_api_key` settings row — not one per provider. Switching providers without supplying a new key leaves whatever key was previously stored in place, even if it belongs to a different provider (in which case calls simply fail with an auth error until a new key is entered).
**Rationale:** The task's own DATABASE section specifies one `ai_api_key` row, not a per-provider map — adding a second schema shape (e.g. a JSON blob keyed by provider) wasn't asked for and would have been a bigger deviation than accepting the tradeoff. The `api_key_source`/`api_key_set` fields on `GET /ai/config` and the Settings UI's badges make the current state visible either way, and switching providers is expected to be followed by entering that provider's own key.

**Decision:** `PUT /settings/{key}` (the pre-existing generic settings endpoint) now explicitly rejects `key == "ai_api_key"` with a 400 pointing at `PUT /ai/config`, and `GET /settings` (also pre-existing, readable by every authenticated role including Read Only) now excludes the `ai_api_key` row entirely from its listing.
**Rationale:** The generic settings endpoints predate this feature and treat every row as an untyped string with no per-key encryption — writing through them would store the API key as plaintext, and reading through them would hand every logged-in user (not just Admins) the Fernet ciphertext. Neither is being newly *exploited* by this change (ciphertext isn't reversible without the app's key), but both are avoidable, and `PUT`/`GET /ai/config` already provide everything a legitimate caller needs (`api_key_set`, `api_key_source`) without ever touching the raw column.

**Decision:** Added `GET /ai/status` (not in the task's endpoint list), open to any authenticated user, returning only `{enabled, configured}` — no provider, model, or endpoint detail.
**Rationale:** Part 5 of the brief requires the invoice review card (used by Standard users, not just Admins, per `docs/user-roles.md`) to show different banners depending on whether AI is disabled or configured — but every other `/ai/*` endpoint is Admin-only per the brief's own instruction. Without a non-admin-safe status check, a Standard user's review card would 403 trying to find out whether to show a banner at all. Same shape as the earlier `GET /settings/terminology` precedent (an otherwise Admin-only settings area carving out one read specifically because every role needs it).

**Decision:** `settings.value` was widened from `VARCHAR(500)` to `VARCHAR(2000)` (migration `0026`), affecting every settings row, not just AI ones.
**Rationale:** Same reasoning as widening `users.mfa_secret` for encryption (migration `0002`, see above): a Fernet ciphertext runs meaningfully longer than the plaintext it wraps, and some providers' API keys are already long before encryption (OpenAI's newer `sk-proj-` keys, for example). There's no separate "AI settings" column family to widen instead — `settings.value` is shared by every key — and a wider column can't break any existing row.

**Decision:** `POST /ai/test`'s 10-per-hour-per-user rate limit reuses the `system_events` table and its existing `recent_attempt_count`-style query pattern (`services/system_reset_service.py`'s own rate limit for `POST /system/reset`), rather than a new table or an in-memory counter.
**Rationale:** `system_events` already exists as exactly this: a lightweight, permanent, DB-backed attempt counter, unrelated to `audit_log` (which the task brief explicitly says *not* to write test results to, "too noisy"). An in-memory counter would reset on every backend restart and wouldn't work if the app were ever scaled to more than one backend process; the DB-backed approach that's already established in this codebase avoids both.

**Decision:** The setup wizard's new AI step (`PUT /auth/setup/ai-config`) is a fourth unauthenticated-but-narrow-window endpoint, following the exact shape of `PUT /auth/setup/app-start-date` (gated by `services.auth_service.sole_setup_admin`, closes forever once a second user exists).
**Rationale:** `POST /auth/setup` never logs the new Admin in (MFA isn't verified yet — see the original auth build's decisions above), so there is no access token available anywhere in the setup wizard flow, and `PUT /ai/config` requires one (`require_admin`). Rather than inventing a different mechanism, the wizard's AI step reuses the identical narrow-window pattern the app-start-date step already established for exactly this problem.

**Not addressed in this pass:** the Custom and Ollama "fetch installed models" flow calls `GET /ai/models` with a live, not-yet-saved endpoint URL — if that URL points at an internal/private address, the backend will make an outbound request to it on the Admin's behalf (SSRF-shaped, though scoped to an Admin-only endpoint hitting `{endpoint}/api/tags` with a 3-second timeout and no credentials attached). Acceptable for a self-hosted/trusted-network feature aimed at Admins, but worth tightening (e.g. blocking loopback/link-local ranges) if this is ever exposed more broadly.

## 2026-08-06 — Full security audit

A line-by-line audit of every file in `backend/` and `frontend/` against authentication/session security, authorisation, injection, data security, infrastructure, API security, frontend security, and dependency vulnerabilities. Full findings and remediation are documented in [security.md](security.md); the decisions below cover fixes with a design tradeoff worth recording.

**Decision:** `config.py`'s `jwt_secret` and `mfa_encryption_key` no longer have a functional default — they default to `""`, and `main.py`'s new `_validate_security_config()` refuses to start the app (raises before the first request is served) if either is missing, too short, or matches a known placeholder/leaked value.
**Rationale:** The previous defaults were a plain "change-me" string for `jwt_secret` and, worse, an actual working Fernet key for `mfa_encryption_key` committed directly in `config.py` — any deployment that forgot to override it via `.env` was silently signing JWTs with, and encrypting every MFA secret under, a key visible to anyone who reads this repository. Failing loudly at startup is disruptive to a misconfigured deployment, but continuing to serve traffic on a publicly known key isn't "working," it's an unprotected system that looks protected — and this repo's own `.env` already has real generated values for both, so this only bites deployments that genuinely never set them.

**Decision:** Rate limiting on `POST /auth/login`, `POST /auth/verify-mfa`, and `POST /auth/register` (`services/rate_limit_service.py`) is keyed by client IP address, not username, and reuses the `system_events` table's existing durable-counter pattern (the same one `system_reset_service` and `ai_provider_service` already use) rather than an in-memory counter or a new dependency.
**Rationale:** Keying by IP means an attacker spamming a real user's username can't use the rate limit itself to lock that user out (a limiter keyed by username would do exactly that). A DB-backed counter survives a backend restart and works the same if this is ever scaled to more than one backend process, matching the precedent already set for `POST /system/reset` and `POST /ai/test`.

**Decision:** A password change (self-service, forced, or an Admin's reset) now stamps a new per-user `users.token_invalid_before` column (migration `0027`), checked in `utils/deps.get_current_user` the same way the existing global `JWT_INVALIDATE_BEFORE_KEY` setting already is — but `PUT /me/password` and `PUT /me/force-password-change` also now return a **fresh** access token (`PasswordChangeOut`) alongside the updated user, rather than leaving the caller's now-invalidated token in place.
**Rationale:** JWTs are stateless and otherwise have no per-user revocation mechanism (see the original auth build's own "logout is stateless" decision above) — without this, a stolen token would keep working for up to its full 8-hour life even after the leaked password was changed. Re-issuing a fresh token for the session that just proved it knows the new password (rather than forcing that same tab to immediately re-authenticate) avoids the alternative of breaking `ProfilePage`'s and `ChangePasswordPage`'s very next API call with a confusing "session invalidated" error moments after a successful save — confirmed this would in fact happen with a live test (see Tested below) before adding the token re-issue. Verified live: an admin password reset or an Admin-forced reactivation both correctly invalidate a *different* user's existing sessions the same way.

**Decision:** `main.py` adds a hard request-body-size ceiling (`max_request_body_bytes`, 10 MB; `max_upload_body_bytes`, 50 MB for `/invoices/upload` and the two `/storage/restore*` routes) checked against `Content-Length` in a middleware, ahead of any endpoint-specific validation.
**Rationale:** No limit existed anywhere in the stack — FastAPI/Starlette impose none by default. A `Content-Length`-based check is coarse (it doesn't stop a client that lies about the header and streams more anyway, or one that omits it and uses chunked transfer), but it's the same class of defence a reverse proxy would normally provide in front of this app, and this app doesn't assume one is there.

**Decision:** Invoice PDF upload validation (`utils/file_validation.py`) now checks the file's own magic bytes (`%PDF-` within the first 1024 bytes) rather than trusting the browser-supplied `Content-Type` header or the `.pdf` filename extension, and rejects anything over 25 MB. Uploaded filenames are also sanitised (control characters, including CR/LF, stripped) before being stored or ever echoed into a response header.
**Rationale:** Both the content type and extension are entirely client-controlled and were the *only* check in place — a non-PDF file renamed to `invoice.pdf` would previously sail straight through to PyMuPDF and the AI extraction call, and an attacker-chosen filename could otherwise land unescaped in a later `Content-Disposition` header. (Starlette's `FileResponse` already RFC-5987-encodes an unsafe filename on the way out, so this wasn't independently exploitable there, but sanitising at the point of ingestion is the correct place to fix it once rather than relying on that downstream behaviour staying true.)

**Decision:** `backup_service.restore_from_zip`'s file-restore loop now resolves each entry's destination path and refuses anything that would land outside `storage_root`, rather than joining the zip's own internal path directly onto disk.
**Rationale:** This is a classic zip-slip: `rel = name[len("files/"):]` came straight from the uploaded zip's own file list, which is attacker-controlled if the "backup" wasn't produced by this app's own `create_backup_zip` (a tampered file, or one from an untrusted source, handed to a Superadmin to restore). Restore is already Superadmin-only and password-gated, but a Superadmin restoring a zip they didn't produce themselves shouldn't be able to have it write files anywhere the backend process can write, just by naming an entry `files/../../../etc/cron.d/x`.

**Decision:** Free-text user input rendered into a generated PDF (invoice supplier/notes, category/group/project names, usernames, report titles, AI-written report summaries) is now escaped (`utils/pdf_text.py`, `xml.sax.saxutils.escape`) before being handed to ReportLab's `Paragraph`.
**Rationale:** `Paragraph` parses its text as a small XML-like markup dialect — `<img src="...">` in particular can reference an external URL that ReportLab will fetch while rendering. A crafted supplier name or report title could otherwise inject markup into every generated invoice/reconciliation export and AI report, including triggering an outbound request (SSRF) the moment someone opens or re-generates that PDF. `canvas.drawString` calls (plain text, no markup parsing) were left alone — only `Paragraph()` call sites needed this.

**Decision:** CSV exports (`utils/csv_export.py`) now prefix any cell starting with `=`, `@`, a tab, or a carriage return with a single quote, and prefix `+`/`-` only when *not* immediately followed by a digit.
**Rationale:** The classic CSV/formula-injection issue — a supplier name or note starting with `=` or `@` would otherwise execute as a formula in whoever's spreadsheet software opens the export. OWASP's own guidance also flags a bare leading `+`/`-`, but this app legitimately exports negative numbers as pre-formatted strings (a reconciliation discrepancy, a year-on-year change) — escaping those unconditionally would turn a real figure into text. Only escaping a sign that *isn't* immediately followed by a digit catches the formula case (`-cmd|...`, `+HYPERLINK(...)`) without mangling `-15.00`.

**Decision:** `CORSMiddleware` now reads its allowed origins from a new `CORS_ORIGINS` env var (comma-separated, default `http://localhost:3000`) instead of `allow_origins=["*"]`.
**Rationale:** Flagged and deliberately left for later in the original auth build ("worth tightening... when deployment URLs are known" — see above); wildcard-plus-credentials is both broader than any real deployment needs and a combination browsers themselves reject. `.env`/`.env.example` were updated to match.

**Decision:** Both Dockerfiles now run as a non-root user (`keeptrack` in the backend image, the pre-existing `node` user in the frontend image), and `docker-compose.yml`'s Postgres port is now published on `127.0.0.1` only instead of every interface.
**Rationale:** Neither service needs root — running as one is more privilege than an API server or a Vite dev server needs and a needless amplifier for any future code-execution bug. Postgres was reachable directly from any host on the network before this change, entirely bypassing the application layer; the backend only ever needs it over the internal Docker network. **Operational note, not silently handled:** an *already-running* deployment's named volumes (`invoice_storage`, `report_storage`, `watched_folder`) were created under the old root-running container and are still owned by root — switching to non-root will hit permission errors writing to them until an operator runs a one-off `docker compose run --user root backend chown -R keeptrack:keeptrack /data` (or recreates the volumes on a fresh deployment, which needs no such step). Verified directly: this repository's own dev stack needed exactly the migration step above, not the chown, since its volumes were fresh enough — see Tested below.

**Decision:** Backend dependency bumps — `python-jose[cryptography]` 3.3.0 → 3.5.0, `python-multipart` 0.0.9 → 0.0.32, `fastapi` 0.115.0 → 0.141.1 (pulling `starlette` 0.38.6 → 1.4.1 transitively) — were applied and verified against the live dev stack; `ecdsa` (a transitive dependency, PYSEC-2026-1325) was left as-is since upstream has no fix and this app never performs an ECDSA operation (JWTs are HS256-only throughout).
**Rationale:** `python-jose` 3.3.0 carried a JWE decompression-bomb DoS reachable simply by POSTing a crafted token to any endpoint that decodes one (`utils/security.decode_token`), regardless of this app only ever issuing HS256 JWS tokens itself — the vulnerable code path is in *decoding*, not signing. `python-multipart` and `starlette` both had multipart/request-parsing CVEs directly reachable through this app's own file-upload endpoints. The `fastapi` jump was large (26 minor versions) and was not applied blindly — see Tested below for what was actually exercised against it before this was committed.

**Not addressed in this pass:** `frontend/package.json`'s `vite`/`esbuild` (dev-server-only CORS/path-traversal CVEs) and `react-router-dom` (an open-redirect CVE in `<Link>`/`useNavigate`) both have fixes available only via a major-version bump (Vite 5→8, React Router 6→7) that `npm audit fix` itself reports as breaking. Neither was applied: this environment has no browser-automation tooling to regression-test all 15+ routes/guards after a router major-version bump, and a blind major bump to the build tool risks breaking `vite.config.js`/the dev workflow in ways that wouldn't surface until someone actually opens the app. Flagged for a follow-up pass with real browser testing available. Separately: this app's `docker-compose.yml` runs `vite dev` as its actual "frontend" service rather than a production `vite build` served statically — the Vite dev server was never designed to be internet-facing, and the specific CVEs here are one symptom of that, not the whole risk; a real production deployment (the k3s manifests layered on top, per `docs/architecture.md`) should build static assets and serve them from a proper static file server rather than running the dev server at all.

**Not addressed in this pass:** JWT access tokens are stored in `localStorage` (`frontend/src/hooks/AuthContext.jsx`), which any successful XSS on the page could read and exfiltrate. No `dangerouslySetInnerHTML`, `eval`, or other injection sink exists anywhere in the frontend (checked directly), and the new strict CSP (`script-src 'self'`, no inline scripts) closes off the most likely injection vector — but moving to an httpOnly cookie would remove the class of risk entirely rather than mitigate it. Not done in this pass: it's a genuine architecture change (CSRF protection, `SameSite` cookie config, every API call, and the backend's own auth flow would all need to change together), disproportionate to fix blind alongside everything else here without dedicated testing.

**Not addressed in this pass:** the real `.env` this deployment is already running has a functional `JWT_SECRET`/`MFA_ENCRYPTION_KEY` (confirmed non-placeholder without printing their values), but `SUPERADMIN_PASSWORD` and `POSTGRES_PASSWORD` are both low-entropy dictionary-style values. Not changed here — rotating either is a credential change with real lockout/downtime risk best left to whoever operates this instance, not silently rewritten mid-audit.

## 2026-08-06 — Suppress zero-entry maintenance notifications

**Decision:** The quarterly audit-log-archive run still always writes its summary `AuditLogArchive` row (`entries_archived` in `extra_metadata`, alongside the existing description) even when it archives zero entries, so `GET /logs/status` and the Audit Log tab still show the run happened — but `routers/dashboard.py`'s live "audit_log_archived" notification now only fires when that count is greater than zero.

Keeping the underlying `AuditLogArchive` row unconditional preserves the existing "task still ran" record (`services/maintenance_service.py`'s own documented rationale for why this goes to `audit_log_archive` rather than `audit_log`, see the invoice/PDF-signing entries above) — only the derived notification is gated.

**Decision:** No equivalent change was made for error-log cleanup's "notification."
**Rationale:** Checked directly: no dashboard notification for `error_log.cleaned` exists anywhere in the app today — `routers/dashboard.py` has no notification block for it, and `frontend/src/pages/DashboardPage.jsx` only special-cases `audit_log_archived`.
